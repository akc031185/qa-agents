Working with GitHub

Never used Git? Perfect — start here. This guide takes you from zero to cloning the agents onto your machine, making a change without breaking anything, getting that change reviewed and approved, and running the agents yourself.

What GitHub actually is

A repository (repo) is the project plus its complete history — every version of every file, and a note explaining each change. Two names to keep straight: git is the version-control tool that runs on your machine and tracks that history; GitHub is the website where the team's shared copy lives, along with reviews and approvals.

The copy on github.com is called the remote. Running git clone gives you your own complete local copy. You work on the local one; push sends your commits up to the remote, and pull brings everyone else's down. Neither side is "the real one" losing data — they're two full copies kept in sync.

One-time setup

You do this once per machine. You'll need Git and Node.js 18 or newer installed — grab them from git-scm.com and nodejs.org, or see GitHub Docs: Set up Git.

  1. Check the tools are there
    git --version
node --version
    WhyBoth should print a version number. Node must report v18 or higher.
  2. Clone the repo
    git clone <repo-url>
    WhyDownloads the entire project and its history into a new folder. The URL comes from the green Code button on the repo's GitHub page.
  3. Step inside it
    cd qa-agent-toolkit
    WhyEvery git and npm command below assumes you're inside the project folder.
  4. Install the dependencies
    npm install
    WhyFetches the libraries the agents need into a local node_modules folder. Run it again any time package.json changes.

Commits = labeled snapshots

A commit is a snapshot of the whole project at one moment, stamped with a message saying why it changed. History is simply a chain of these snapshots — you can walk back through it, compare any two points, or revert to one when something goes wrong. That's the safety net: nothing committed is ever truly lost.

Making one is two moves: stage what you changed, then commit it with a message.

git add -A                          # stage every change you made
git commit -m "Explain the change"  # snapshot it, with the why
Write messages for humans. "Fix login timeout on slow networks" beats "changes". Six months from now, the message is the only clue to why the code looks the way it does.

Branches: change things without touching main

main is the source of truth — the version everyone trusts and runs. You never experiment on it directly. Instead you make a branch: a parallel line of commits with its own name, where you can work in isolation. When your work is reviewed and approved, it merges back into main. See GitHub Docs: About branches.

Without a branch

Every half-finished edit lands straight on main. One broken commit and the whole team's copy of the agents stops working — and untangling it is painful.

→
With a branch

Your work lives on its own named line. main stays green the whole time, teammates keep working, and your change only joins after review. Worst case, you delete the branch and lose nothing.

git switch -c fix-login-timeout        # create the branch and hop onto it
git add -A                             # ...make your edits, then stage them
git commit -m "Retry login on slow networks"
git push -u origin fix-login-timeout   # publish the branch to GitHub

Pull requests & approvals

Once your branch is pushed, you open a pull request (PR) on github.com — literally a request to pull your branch into main. GitHub shows teammates the exact diff (every line added or removed), and they comment, request changes, or approve. When it's approved and the automated checks pass, one click merges it into main.

This is the team's review-and-approval gate: nothing reaches main un-reviewed. It's also where discussion lives, attached forever to the change it was about. Full walkthrough at GitHub Docs: Pull requests.

After any merge, sync up. Run git pull on main to bring the newly merged work — yours or a teammate's — down to your machine before starting the next thing.

Run the agents from the repo

Cloned and npm install-ed? Then you're three commands from seeing the toolkit work — no accounts, no credentials, no live systems needed for the demos.

  1. Copy the environment template
    cp .env.example .env
    Why.env holds your settings and secrets, and git ignores it so they never get committed. Fill in only the section you actually need — everything else can stay blank.
  2. Sanity-check your setup
    npm run doctor
    WhyPrints which capabilities are switched on given what's in your .env. Blank env? That's fine — it just reports the offline-friendly parts as ready.
  3. Run the reusable demos — zero credentials required
    npm run demo:ado      # tracker connector, against sample data
npm run demo:report   # builds a self-contained web report
npm run demo:api      # API tester, with an evidence log
npm run demo:db       # data-verification engine
    WhyEach one exercises a toolkit module end-to-end on bundled sample data, so you can watch what it produces before pointing it at anything real.
Which agents run standalone? Only the 5 toolkit modules run like this, on sample data with no setup. The other 33 agents need the live systems they were built to talk to — a project tracker, the app's API, the design files — so treat their pages as reference until those connections exist.

The daily loop

Everything above compresses into one cycle you'll repeat until it's muscle memory. Start every piece of work by pulling, end it with a merged PR, and go around again.

git pull                          # 1 · start fresh with everyone's latest
git switch -c my-change           # 2 · branch off main
                                  # 3 · ...edit files...
git add -A && git commit -m "..."  # 4 · snapshot the change
git push -u origin my-change      # 5 · publish the branch
                                  # 6 · open a PR on github.com, get it approved, merge
Feeling lost mid-loop? git status is always safe to run — it tells you which branch you're on and what's changed but not yet committed. When in doubt, status first.

Command cheat-sheet

The eight moves that cover 95% of daily work. Bookmark this bit.

git clone <url>
Copy the repo — project plus full history — onto your machine. Once per machine.
git status
Where am I, and what have I changed? Always safe; run it constantly.
git switch -c <name>
Create a new branch and move onto it in one step.
git add -A
Stage all your changes, ready to be committed.
git commit -m "why"
Snapshot the staged changes, with a message explaining the why.
git push -u origin <name>
Send your branch and its commits up to GitHub.
git pull
Bring the latest merged work down from GitHub to your machine.
open a PR
Done on github.com: pick your branch, request review, merge when approved.
