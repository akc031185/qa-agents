What's inside

The four building blocks

Each block is a small, tested piece you can drop into a project. The number on the right is how much hand-written, copy-pasted code it replaces.

Talk to the project tracker

One connector for the team's shared to-do board (Azure DevOps) — create, link, and update cards, or run entirely offline against sample data when there's no cloud.

~85scripts unified into 1

Build the reports people read

One design kit that turns any tool's results into a clean, self-contained web page — dashboards, tables, and pass/fail grids that all look like one product.

~90page-builders unified into 1

Test a live service

One tester that calls an app's service counter (its API), keeps a record of every request and reply as evidence, and retries when the network hiccups.

~96scripts unified into 1

Check the data is right

One engine that compares what the app says against what its records actually hold — even for databases locked behind a company firewall, via a shared-folder relay.

7ways to compare, 1 engine
The one clever idea

It notices what it's allowed to do, and adjusts.

The usual way

Most automation assumes the whole cloud is present. Hand it to a new team without the right cloud accounts and it fails at the first step.

→
This toolkit

On startup it checks which credentials exist and switches each of the four jobs on or off accordingly. Missing the cloud? The tracker runs against sample data, and everything else still works. Nothing crashes; it just does what it can.

Try it

Runs in a minute — no credentials required

Every demo below works on a fresh machine with nothing configured. That's the point: the toolkit is real, and anyone can run it.

$ npm install $ npm run doctor # shows which parts are switched on # Each demo runs with NO accounts or passwords: $ npm run demo:ado # find a task → file a bug → record results (offline) $ npm run demo:report # build a self-contained web dashboard $ npm run demo:api # test a public service, with evidence $ npm run demo:db # compare records seven different ways
Why it exists

The same plumbing, written by hand, over and over

Before the toolkit, the identical low-level code was re-created on project after project. Counted across the original work:

~85places the same tracker sign-in code was copy-pasted — now one connector.
~90report pages that each re-invented their own layout — now one design kit.
~96scripts that re-wrote the same service-call boilerplate — now one tester.

How it's laid out

src/core/ config · types · llm · theme · ado · html · api · db (the typed core) src/cli/ doctor (capability check) agents/ ado · api · db · report (composable agents) examples/ demo.ts per domain — all runnable offline fixtures/ synthetic sample data (no real records) docs/domains/ one reference doc per building block docs/site/ this field guide (contents · plates · slides)

Written in TypeScript (strict). Credentials come from the environment only — nothing sensitive is ever stored in the code. Licensed MIT.
