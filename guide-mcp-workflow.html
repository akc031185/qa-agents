Workflows on an MCP server

Stand up a free, local MCP server in ~60 lines of TypeScript, and let Claude monitor and execute a workflow through tools you control. Local files, stdio transport, nothing to pay for.

What MCP is

Model Context Protocol (MCP) is an open-source standard for connecting AI applications to external systems. Think of it like a USB-C port for AI: just as USB-C provides a standardized connector, MCP provides a standardized way for AI clients (like Claude) to call tools (functions) and read resources (read-only data) exposed by servers you control.

With MCP, Claude can call custom tools you define (e.g., "check queue status" or "execute next workflow step"), access read-only resources you expose (workflow definitions, logs, config files), and do all of this securely, on your machine, with no cloud dependencies.

Two names to keep straight: the client is Claude Code (CLI) or the Claude Desktop app — it launches the server and makes tool calls. The server is a program you write that exposes tools and resources.

Transport: stdio (local) vs HTTP (remote)

MCP servers communicate via transports, and the choice decides your bill.

HTTP / SSE — remote

The server is hosted on a URL. Cost depends on hosting; setup requires a server, a domain, possibly a cloud bill. Right for shared, remote services — overkill for today.

→
Stdio — local (this guide)

Your machine launches the server as a child process and talks to it over stdin/stdout using JSON-RPC. Free, minimal setup, command line only. No network, no cloud bill, entirely local.

The plan: a workflow monitor + executor

We'll build a minimal local MCP server with exactly two tools, backed by nothing fancier than a queue/ folder on disk:

monitor_workflow
Reads a local queue directory (or status file) and returns the current workflow state — e.g., checks ./queue/pending/ and returns the list of pending jobs, their statuses, and the next action.
execute_workflow
Runs the next workflow step — e.g., moves the first file from pending/ to running/, updates the status log, and returns confirmation of the action taken.
User: "Check the workflow queue and execute the next pending item"
  ↓
Claude calls: monitor_workflow()
  ↓ (gets list of pending jobs)
Claude calls: execute_workflow(job_id)
  ↓ (moves file, updates log)
Claude reports: "Started job XYZ, moved to running/"
Why this design? It's free (runs on local files — no database, no API, no bill), simple (~50–60 lines of TypeScript server code), real (models actual workflow automation: monitor state, trigger actions), and extensible (easy to replace the file system with a database, HTTP call, or shell command).

Build the server

All you need: Node.js 18+ (Bun or Deno work too, but Node is standard), npm or your preferred package manager, and a terminal.

  1. Create the project structure
    mkdir workflow-mcp-server
cd workflow-mcp-server
npm init -y
    WhyA fresh folder with a default package.json — the usual Node starting point.
  2. Install dependencies
    npm install @modelcontextprotocol/sdk zod
npm install --save-dev typescript @types/node ts-node
    Why@modelcontextprotocol/sdk is the official MCP SDK for TypeScript; zod handles schema validation for tool inputs (required peer dependency); typescript, @types/node, and ts-node are the TypeScript tooling.
  3. Configure TypeScript — create tsconfig.json
    {
  "compilerOptions": {
    "target": "ES2020",
    "module": "commonjs",
    "lib": ["ES2020"],
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules"]
}
    WhyCompiles everything in src/ to plain JavaScript in dist/, in strict mode.
  4. Create the server code — src/server.ts
    import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import {
  CallToolRequestSchema,
  ListToolsRequestSchema,
  Tool,
} from "@modelcontextprotocol/sdk/types.js";
import * as fs from "fs";
import * as path from "path";
import { z } from "zod";

// Initialize the server
const server = new Server({
  name: "workflow-monitor",
  version: "1.0.0",
});

// Define tool input schemas
const MonitorSchema = z.object({
  queue_dir: z.string().default("./queue/pending"),
});

const ExecuteSchema = z.object({
  job_id: z.string(),
});

// Tool 1: Monitor workflow queue
async function monitorWorkflow(
  args: Record<string, unknown>
): Promise<string> {
  const { queue_dir } = MonitorSchema.parse(args);

  if (!fs.existsSync(queue_dir)) {
    fs.mkdirSync(queue_dir, { recursive: true });
  }

  const files = fs.readdirSync(queue_dir);
  if (files.length === 0) {
    return JSON.stringify({
      status: "idle",
      pending_jobs: [],
      message: "No pending workflow items",
    });
  }

  return JSON.stringify({
    status: "has_jobs",
    pending_jobs: files,
    count: files.length,
    message: `Found ${files.length} pending job(s). Next: ${files[0]}`,
  });
}

// Tool 2: Execute workflow step
async function executeWorkflow(
  args: Record<string, unknown>
): Promise<string> {
  const { job_id } = ExecuteSchema.parse(args);

  const pending_dir = "./queue/pending";
  const running_dir = "./queue/running";
  const job_file = path.join(pending_dir, job_id);

  if (!fs.existsSync(job_file)) {
    return JSON.stringify({
      success: false,
      error: `Job ${job_id} not found in pending queue`,
    });
  }

  if (!fs.existsSync(running_dir)) {
    fs.mkdirSync(running_dir, { recursive: true });
  }

  // Move file from pending to running
  const dest = path.join(running_dir, job_id);
  fs.renameSync(job_file, dest);

  // Append log entry
  const log_file = path.join(running_dir, ".log");
  const timestamp = new Date().toISOString();
  fs.appendFileSync(
    log_file,
    `[${timestamp}] Started job: ${job_id}\n`
  );

  return JSON.stringify({
    success: true,
    job_id,
    moved_to: "queue/running",
    timestamp,
    message: `Job ${job_id} moved to running state`,
  });
}

// Register tools with the server
server.setRequestHandler(ListToolsRequestSchema, async () => {
  return {
    tools: [
      {
        name: "monitor_workflow",
        description:
          "Monitor the workflow queue and report pending jobs",
        inputSchema: {
          type: "object" as const,
          properties: {
            queue_dir: {
              type: "string",
              description: "Path to the pending queue directory",
            },
          },
          required: [],
        },
      } as Tool,
      {
        name: "execute_workflow",
        description: "Execute the next pending workflow step",
        inputSchema: {
          type: "object" as const,
          properties: {
            job_id: {
              type: "string",
              description: "ID of the job to execute",
            },
          },
          required: ["job_id"],
        },
      } as Tool,
    ],
  };
});

// Handle tool calls
server.setRequestHandler(CallToolRequestSchema, async (request) => {
  const { name, arguments: args } = request.params;

  try {
    let result: string;
    if (name === "monitor_workflow") {
      result = await monitorWorkflow(args || {});
    } else if (name === "execute_workflow") {
      result = await executeWorkflow(args || {});
    } else {
      return {
        isError: true,
        content: [{ type: "text", text: `Unknown tool: ${name}` }],
      };
    }

    return {
      content: [{ type: "text", text: result }],
    };
  } catch (error) {
    return {
      isError: true,
      content: [
        {
          type: "text",
          text: `Error: ${error instanceof Error ? error.message : String(error)}`,
        },
      ],
    };
  }
});

// Start the server
async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error("Workflow MCP server running on stdio transport");
}

main().catch((error) => {
  console.error("Server startup error:", error);
  process.exit(1);
});
    WhyThe whole server: two zod input schemas, two tool functions over the file system, a handler that lists the tools, a handler that routes calls to them, and a stdio transport to talk to Claude.
  5. Build & test the server
    npx tsc
node dist/server.js
    WhyIf you see Workflow MCP server running on stdio transport with no errors, it's working. Press Ctrl+C to stop.
Note: The server stays running waiting for input. This is normal — it waits for Claude to send tool calls.

Connect it to Claude

Option A: using claude mcp add (recommended)

From your project directory, run:

claude mcp add workflow-server -- node dist/server.js

What this does: claude mcp add registers the server with Claude Code; workflow-server is the name you give the server (shows up in Claude's output); -- separates the server name from the command; and node dist/server.js is the command Claude Code will run to start your server.

Option B: edit .mcp.json manually

Create (or edit) .mcp.json in your project root:

{
  "mcpServers": {
    "workflow-server": {
      "type": "stdio",
      "command": "node",
      "args": ["dist/server.js"]
    }
  }
}

Then start Claude Code in the project:

claude

Verify the connection

In your terminal (outside Claude), check the server list:

claude mcp list

You should see:

✔ Connected · workflow-server

Inside a Claude session, you can also run /mcp — it shows all connected servers and their tools.

Seeing ✘ Failed to connect? Troubleshoot in order: 1) ensure dist/server.js exists (ls dist/server.js); 2) try running it directly with node dist/server.js — it should output "Workflow MCP server running on stdio transport"; 3) check for typos in .mcp.json or the claude mcp add command.

Run the workflow

  1. Set up test data
    mkdir -p queue/pending queue/running
echo "job-001-process-report" > queue/pending/job-001
echo "job-002-send-email" > queue/pending/job-002
    WhyTwo fake jobs in the pending queue give Claude something real to monitor and execute.
  2. Start Claude Code
    claude
    WhyClaude Code launches your MCP server as a subprocess and discovers its two tools.
  3. Ask Claude to monitor & execute
    Check the workflow queue and execute the first job.
    WhyWhat happens: 1) Claude calls monitor_workflow() and gets the list of pending jobs; 2) Claude calls execute_workflow(job_id="job-001-process-report"); 3) the server moves the file from queue/pending/ to queue/running/; 4) Claude reports the result.
  4. Check what happened
    ls queue/running/  # Should see job-001-process-report
cat queue/running/.log  # Should see execution timestamp
    WhyThe file system is the workflow state — you can always verify it directly, outside Claude.
  5. Automate a loop
    Keep executing workflow jobs one at a time until the queue is empty.
Report after each execution.
    WhyClaude will loop, calling monitor_workflow() to check for more jobs, then execute_workflow() until the queue is empty.

What you've built

Free · local Two tools Stdio transport File-based state

A free, local MCP server (no cloud bill) with two tools exposed to Claude via the MCP protocol, running over stdio transport (local subprocess, secure, fast), with workflow state tracked via the local file system and Claude integration via claude mcp add or .mcp.json.

The pattern generalizes: replace the file system with database queries; add tools for sending emails, calling APIs, or running shell commands; monitor external systems (CI/CD status, deployment queues, bug trackers); execute remediation (auto-retry, escalate, notify).

Extend the server

complete_workflow()
Add a third tool that moves finished jobs to queue/done/.
resources
Expose the log file as a read-only MCP resource — Claude can fetch it with @workflow-logs.
validation
Require job metadata (owner, priority, deadline) in the queue items.
error recovery
Implement retry logic in execute_workflow().
