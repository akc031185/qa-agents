The Spec Reverse-Engineer

Reconstructs a feature's spec — description, acceptance criteria, scope — from its test cases alone, grounded only in what the tests evidence.

Source file: tc-spec-agent.ts

Recovers the written spec when tests exist but the specification was never finished or was lost. Reads the test cases, groups them by story, and reverse-engineers a feature description plus a list of acceptance criteria straight from what the steps and expected results actually assert — no invented requirements.

Why this exists

The chore it removes

Documenting a feature that has dozens of test cases but no spec is slow detective work: read every test, infer the behavior each one proves, group by topic, then write a description, acceptance criteria, and in/out-of-scope notes. It's manual, and two analysts produce two different write-ups.

→
What you get instead

The agent loads the test cases, buckets them by parent story, and calls the LLM to emit a description, an acceptance-criteria list, and in-scope/out-of-scope notes per group — constrained to what the tests evidence, never inventing requirements. Outputs Word, Markdown, and JSON.

A feature with no spec is one nobody can safely change. Reconstructing the description turns undocumented behavior back into something the team can reason about and regression-test against.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Read access to Azure DevOps and a personal access token (ADO_PAT) — OR an xlsx export of test cases if you'd rather not connect live.
  • A Google Gemini API key — this agent always calls the LLM to write the description and criteria.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program executed under Node. One-time install per machine.
    First run First time on a new machine only.
  2. Clone the code and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install resolves the agent's dependencies — the ADO REST client, the xlsx reader, the docx writer, and the Gemini client — into node_modules.
    First run Downloads everything (a minute or two).
    Re-run No-op unless the dependency set changed.
  3. Set the environment variables.
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
export GOOGLE_API_KEY=your-gemini-key
    Why Read at startup: the ADO org/project to query, the PAT that authorizes it, and the Gemini key that writes the spec. Skip the ADO vars entirely if you're loading from an xlsx file.
  4. Dry-run first — inspect the loaded test cases without an LLM call.
    npx ts-node agents/tc-spec-agent.ts --feature-id 5001 --dry-run
    Why --dry-run loads and groups the test cases as normal but skips the LLM step, so you can confirm it resolved the right tests before spending model calls.
    First run Prints the grouping only — no description or criteria yet.
  5. Run for real, from whichever source you have.
    # From a feature's test cases in ADO:
npx ts-node agents/tc-spec-agent.ts --feature-id 5001 --word

# Or from an xlsx export of test cases:
npx ts-node agents/tc-spec-agent.ts --excel ./inputs/test-cases.xlsx --word
    Why Drop --dry-run to call the LLM. --feature-id pulls every test case under a feature; --excel reads them from a spreadsheet — pick whichever matches where your tests live. --word also emits a docx.
    First run Groups the tests by story, reverse-engineers each group's spec via the LLM, and writes the outputs.
    Re-run No change-tracking — every run recomputes fresh; re-run whenever the test cases change.
  6. Open the reconstructed specification.
    open ./outputs/reports/tc-spec/
    Why Outputs land as JSON, Markdown, and — with --word — a docx, one section per group of test cases.

What you give it

--feature-id <id> | --story-ids <ids> | --tc-ids <ids> | --excel <path>
The test-case source — pick exactly one.
--word / --dry-run
--word also emits a Word document; --dry-run skips the LLM call and just prints the grouping.
environment variables
ADO_ORGANIZATION, ADO_PROJECT, ADO_PAT (if using ADO), and GOOGLE_API_KEY.

What comes back

TcSpec_<label>_<timestamp>.json / .md
One section per group of test cases — description, acceptance criteria, in-scope/out-of-scope notes.
TcSpec_<label>_<timestamp>.docx
The same content as a shareable Word document (only with --word).
Running it again. No fingerprinting or change-tracking — every run reads the current test cases fresh and re-queries the LLM. Re-run whenever the underlying test cases change or after adding new ones; treat each run's output as the latest snapshot, not a diff against the prior one.
Plug it into your stack. Reach for this when a feature has tests but no spec — hand the output to the Requirements Sharpener or straight to stakeholders as the 'what this feature actually does' reference. Works as a one-off audit tool or scheduled to catch specs that went stale.
