The Test Scheduler

Load-balances a feature's test cases across the team by weighted priority and emits a phased schedule as Word and Excel deliverables.

Source file: test-execution-planner-agent.ts

Automates test-execution planning: pulls live test-case counts from ADO, distributes stories across the team so no one is overloaded, lays a phased timeline on business days, assesses risk, and renders stakeholder-ready Word and Excel documents. Removes the half-day of manual spreadsheet math a lead does every sprint.

Why this exists

The chore it removes

Before every sprint a lead builds the plan by hand: count each story's test cases, estimate capacity, assign urgent stories to the right people, sketch a timeline, enumerate risks, and format it into something management will read. It takes half a day, the weighting math is error-prone, and one tester silently ends up overloaded.

→
What you get instead

Give it the feature ID, the team roster, and the sprint dates. It reads the real test-case counts, balances load by weighted priority (P1 counts 1.5x, P4 only 0.3x), builds a phased timeline with milestones on business days, runs rule-based risk checks, and writes the Test Plan and Execution Schedule as Word and Excel — no hand-formatting.

A weighted, business-day-accurate schedule is the difference between a sprint that lands on time and one where the busiest tester becomes a silent bottleneck.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Read access to Azure DevOps and a personal access token (ADO_PAT).
  • The feature's stories must already have test cases linked (the Test-Plan Author produces these) — counts are pulled live.
  • The team roster and the sprint's start/end dates.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program executed under Node. One-time install per machine.
    First run First time on a new machine only.
  2. Clone the code and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install resolves the agent's dependencies — the ADO REST client and the docx/xlsx writers — into node_modules.
    First run Downloads everything (a minute or two).
    Re-run No-op unless the dependency set changed.
  3. Set the environment variables.
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
    Why Read at startup: the ADO org/project to query and the PAT that authorizes it. No LLM key needed — this agent is deterministic scheduling math, no model calls.
  4. Dry-run first — print the numbers without writing files.
    npx ts-node agents/test-execution-planner-agent.ts \
  --feature-id 5001 \
  --team "Alex P|Jordan K|Sam R|Taylor M" \
  --sprint Sprint-12 \
  --start-date 2026-08-03 --end-date 2026-08-14 \
  --dry-run
    Why --team is a pipe-separated roster; --dry-run prints story count, total test cases, and team size to stdout without writing files — a sanity check before the real run.
    First run Prints a one-screen summary only.
  5. Run for real; add --word for the formatted documents.
    npx ts-node agents/test-execution-planner-agent.ts \
  --feature-id 5001 \
  --team "Alex P|Jordan K|Sam R|Taylor M" \
  --sprint Sprint-12 \
  --start-date 2026-08-03 --end-date 2026-08-14 \
  --word
    Why Drop --dry-run, add --word. Writes the balanced schedule, timeline, risks, and milestones to disk, plus a Test Plan and a Test Execution Plan docx.
    First run Computes the full schedule and writes every file.
    Re-run No fingerprinting — recomputes fresh. Re-run whenever the team, dates, or story list change.
  6. Open the results.
    open ./outputs/reports/test-plans/
    Why JSON, Markdown, an xlsx workbook (one sheet per member), and — with --word — the two docx files, all in one folder.

What you give it

--feature-id <id>
The feature to schedule — its stories and linked test-case counts are pulled live from ADO.
--team "Name1|Name2|..."
Pipe-separated roster to balance the load across.
--sprint <name> --start-date <date> --end-date <date>
The sprint label and its calendar start/end dates, used to size the phased timeline in business days.
--word / --dry-run
--word also emits the Word documents; --dry-run prints the summary and writes nothing.

What comes back

ExecutionPlan_<id>_<timestamp>.json / .md
The full computed plan — weighted workload, timeline, milestones, risks — machine- and human-readable.
ExecutionSchedule_<id>_<timestamp>.xlsx
An xlsx workbook with a sheet per team member plus a combined assignments view.
TestPlan_<id>_<timestamp>.docx / TestExecutionPlan_<id>_<timestamp>.docx
Two Word documents (only with --word) — a stakeholder-ready Test Plan and a day-by-day Test Execution Plan.
Running it again. No fingerprinting — every run recomputes the schedule from the feature's current story and test-case counts. Re-run whenever the roster, sprint dates, or story list change; each run gets a fresh timestamp so nothing is overwritten.
Plug it into your stack. Consumes the test-case counts the Test-Plan Author produced. Run at sprint planning and again on any mid-sprint scope shift — the risk flags (overload, short sprint, uneven distribution) are worth re-checking each time.

A typed list of risks — overload, too-short sprint, uneven distribution — each with a mitigation.

JSON and Markdown, an xlsx workbook with one sheet per member, and — with --word — a Test Plan and a Test Execution Plan docx.
