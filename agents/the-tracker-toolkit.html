The Tracker Toolkit

One typed Azure DevOps client every agent shares — reads and writes work items live, or against local fixtures with zero credentials.

Source file: src/core/ado.ts

A single AdoClient that reads and writes ADO work items — stories, bugs, test points, test runs — for every agent in the toolkit. It replaces ~85 scripts that each re-implemented the same base64 auth header and hard-coded one org/project/board. Org, project, and PAT now come from config; drop the PAT and the identical client transparently backs onto a fixtures/ado FixtureStore, so the same code path runs in CI with no network and no secrets.

Why this exists

The chore it removes

The prior setup had ~85 scripts, each re-implementing the same Basic base64(':' + PAT) auth and each with the org, project, and board URL baked in. Rotating a PAT or switching boards meant hand-editing dozens of files. And none of them ran without a live board and a valid PAT — no offline demo, no unit-testable path.

→
What you get instead

One client. Auth is defined once; apiBase, project, and testPlanId come from loadConfig().ado, so nothing is tied to a specific tenant. When no PAT is present the constructor flips offline: true and routes every call through a FixtureStore over fixtures/ado/{id}.json — same methods, same return types, no network. Live and offline are chosen automatically by whether a PAT exists.

One typed, config-driven client replaces ~85 fragile single-purpose scripts. Point it at any tenant via env vars, or at fixtures for a credential-free demo — the calling code is identical either way, so the same agents run in CI and in production.

What this step does

See it in action

Run it & wire it in

You can run this yourself, end to end — every command below is real.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Node.js (installed in step 1 below) — nothing else.
  • No credentials, board, database, or API key are needed for the demo below — that is the point of this module. A .env only matters later, if you point it at something real.

Step by step

  1. Install Node.js — the runtime.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The toolkit is TypeScript on Node. One install per machine; no other runtime required.
    First run First time on a new machine only.
  2. Clone and install dependencies.
    cd path/to/qa-agent-toolkit
npm install
    Why npm install pulls the toolkit's only dependency (dotenv) into node_modules. No DB driver, no cloud SDK, no auth library — which is why the demos run credential-free.
    First run Downloads everything (seconds — the dependency list is tiny).
    Re-run No-op unless the dependency list changed.
  3. (Optional) copy the env template — only to go live later.
    cp .env.example .env
# then open .env and fill in ONLY the section you need
    Why Skippable for the demo — every capability is off by default and the demo runs on fixtures regardless. .env matters only once you point the toolkit at a real board, service, or database.
  4. Run the capability check.
    npm run doctor
    Why Prints a one-line scorecard per capability (tracker, API, database, AI) — on/off with a reason. With an empty .env everything reads (off), which is expected: the demo needs none of them on.
  5. Run the tracker demo — query a story, file a bug, post outcomes.
    npm run demo:ado
    Why Exercises the real AdoClient end to end against fixtures/ado (offline: true, no PAT): queries a User Story via WIQL, files a bug from a synthetic TestFailure, and derives + posts Test Case outcomes — the same code path a live board takes.
    First run Reads the fixture story, files an in-memory bug (persist: false, so committed fixtures are never modified), and prints the derived Test Case outcomes.
    Re-run Deterministic — fixtures never change, so a second run prints the identical story, bug fields, and Passed/Failed outcomes.
  6. Read the terminal output.
    # nothing to open — this demo prints straight to the terminal:
#   1. Query a User Story (WIQL)
#   2. File a Bug from a test failure
#   3. Derive Test Case outcomes and post a run
#   4. Summary
    Why No file output; the log is the evidence — the story found (#101), the bug filed (#204, in-memory only), and the 3 derived Test Case outcomes (2 Passed, 1 Failed).

What you give it

nothing
Runs on the committed fixtures/ado/*.json — sample story, child tickets, and test cases. No board, PAT, or network.
ADO_ORG / ADO_PROJECT / ADO_PAT (optional)
Set all three in .env to point the same client at a real Azure DevOps board; offline flips to false automatically once a PAT is present.

What comes back

console log
The story found, the bug filed (id, title, severity, links), and each Test Case's derived outcome (Passed/Failed) with its reason — all printed, nothing written to disk.
in-memory bug #204
Created for the demo only (persist: false); fixtures/ado is never touched, so the demo is safe to rerun indefinitely.
Running it again. Idempotent: the demo runs with persist: false, so nothing it creates is written back to the fixtures — rerun freely and get the identical story, bug, and outcomes. Point the same client at a live board (set ADO_PAT) and reruns instead reflect the board's current state.
Plug it into your stack. Import directly: import { AdoClient } from './src/core/ado', then new AdoClient({ config: loadConfig().ado }) — with a PAT it hits the live board, without one it falls back to fixtures, so the same calling code runs in CI (offline) and production (live). Compose with BugFilerAgent (agents/ado/bug-filer-agent) and TestResultsAgent (agents/ado/test-results-agent) exactly as examples/ado/demo.ts does.

When fileOne is called on a TestFailure.

Test name, error, and optional parentId.
Shows out
A created bug, a reused open one (dedupe), or a would-create preview (dryRun), parent-linked.

Test-case ids with their outcomes.

A completed test run — live on the real plan or in the fixture store — readable back for reporting.
