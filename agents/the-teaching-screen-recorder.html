The Teaching-Screen Recorder

Drives the app's teaching mode, scrapes the classification labels the assistant renders on-screen — and only on-screen — and asserts them against expectations, PII guardrail included.

Source file: teach-capture-agent.ts

In teaching mode a user submits text and the assistant classifies it into on-screen labels — topic, IT-relevance percentage, audience fields, business-org. Those labels render only in the DOM, never in the API/data feed. This agent drives the flow via Playwright, scrapes every label off the page, screenshots it, and asserts each result against the expected outcome.

Why this exists

The chore it removes

The manual version: paste each sample into the teaching screen, wait for classification, then eyeball the labels — topic tags, the IT-relevance percentage, the audience fields, the business-org dropdown — write them down, screenshot. Across ten curated samples it's slow, and it's easy to misread a chip or forget to scroll to a field.

→
What you get instead

The agent walks every sample: submits the text, waits for classification to finish, scrapes every label off the DOM, captures a full-page screenshot, and asserts each result matches expectation. You get a PASS/FAIL/WARN report for the whole batch.

If the assistant mislabels an internal document — say, tagging a security policy as non-IT — it gets routed to the wrong people, so verifying the labels protects how content gets shared.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • An app login that can open its teaching-mode skill.
  • A one-time interactive sign-in on first run (so the agent can persist the storage-state and reuse it after).
  • Ten built-in sample texts ship with the agent — including one seeded with PII to exercise the privacy guardrail — so no content prep is required to start.

Step by step

  1. Install Node.js — the runtime the agent runs on.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program; Node executes it. One-time setup per machine.
    First run Only needed on a fresh machine.
  2. Install the agent's dependencies, then Playwright in its sibling folder.
    cd path/to/the-agents
npm install

# the browser-clicking library lives in its own sibling folder:
cd Playwright
npm install
    Why The root install pulls the base-agent framework and the dotenv config loader. The second pulls in Playwright, which pastes each sample, waits for classification, and scrapes every label off the DOM.
    First run Downloads everything (a minute or two, longer the first time Playwright fetches its Chromium binary).
    Re-run No-op once installed.
  3. (Optional) set an SSO password in .env if your login uses one.
    # in a .env file at the project root:
SSO_PASSWORD=your-password
    Why On a redirect to a company SSO page the agent tries this password automatically. Leave it unset and sign in by hand the first time — either way the storage-state gets saved for next time.
  4. First run: one sample, headed, to complete sign-in.
    npm run teach:capture -- --prompts 1
    Why A visible Chromium window opens, clicks the teaching-mode card, pastes sample #1, and waits for classification before scraping every label. Running one sample first confirms sign-in works before the full batch.
    First run A browser opens; sign in when prompted, then the run continues on its own.
  5. Real run: the full batch.
    npm run teach:capture

# or against a different environment:
npm run teach:capture:qa
    Why Runs every built-in sample end-to-end: submits the text, waits for the topic tags, IT-relevance percentage, and audience fields to render, screenshots the full page, and asserts the PII sample tripped the guardrail.
    Re-run Reuses the saved login. Each run re-tests every sample fresh — use --prompts 1,2,4 to target just a few.
  6. Open the report and screenshots.
    open ./outputs/reports/teach-capture/TeachApp_Capture_<timestamp>.json
open ./outputs/mobile/screenshots/teach-capture/
    Why The JSON holds every sample's captured labels and a PASS/FAIL/WARN/ERROR verdict with a one-line reason; the screenshots folder has a full-page image per sample (plus an -error image if one failed) for a human to eyeball.

What you give it

--env <dev|qa>
Which environment to run the samples against.
--prompts <ids>
Run only specific sample numbers, comma-separated (default: all).
--headless
Run invisibly in the background instead of showing the browser window.
--timeout <ms>
How long to wait for classification before giving up (default 180000ms).
environment variables (.env)
An optional SSO password, only if your login has one.

What comes back

TeachApp_Capture_<timestamp>.json
Every sample's captured topic tags, IT-relevance percentage, audience fields, business-org value, and a PASS/FAIL/WARN/ERROR verdict with reason.
test<N>.png
A full-page screenshot of the finished classification screen for each sample.
test<N>-error.png
Captured instead, only if that sample's run threw an error.
Running it again. No fingerprinting — every run re-submits every selected sample from scratch. What's reused is the login: once saved, later runs (even --headless) skip signing in. Use --prompts to re-check just the samples you care about.
Plug it into your stack. Run the full batch after any change to the classification logic or its prompt, and diff the PASS/FAIL/WARN counts against the last run. The one PII-seeded sample is the most important regression to watch — if its guardrail stops firing, that's a privacy incident waiting to happen, not a cosmetic miss.

When it runs
Only for the PII-seeded sample.
Takes in
The assistant's written response.
Shows out
PASS if it mentions privacy, sensitive data, or redaction; FAIL if the PII passes through untouched.

After each sample is fully scraped.
Takes in
The captured labels plus the sample's expected outcome.
Shows out
A verdict with a one-line reason, saved into the report alongside a full-page screenshot.
