Finding & reporting problems

The Bug Analyst

Rolls every bug under a feature into a computed status report — fix rate, time-to-fix, hotspots, per-assignee load — with zero manual tallying.

Source file: bug-intelligence-agent.ts

Walks a feature (or an explicit story list) down to its child Bug work items, enriches each with a computed days-to-fix, aggregates the whole set in memory, and emits a shareable report set: JSON, Markdown, a multi-sheet Excel workbook, and optionally Word. Replaces the afternoon-in-spreadsheets with a single deterministic pass.

Why this exists

The chore it removes

Briefing a lead means opening the tracker and hand-tallying: open vs fixed, severity mix, which area has the most, who's carrying the load, mean time-to-fix — then pasting it into a doc. Hours of work, stale the next day, and arithmetic errors creep in by hand.

→
What you get instead

An instant, reproducible report — totals by severity/state, fix rate, average days-to-fix, the hotspot story, per-assignee workload, plus generated insights and recommendations — as Markdown, Excel, JSON, and optionally Word. Every number is computed from live tracker data, so it's right every run.

Go/no-go calls ride on these numbers. Getting them fast and correct is the difference between a confident ship and a nasty surprise — and computed beats hand-tallied every time.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • An Azure DevOps org/project and a PAT with work-item read scope.
  • A feature ID (top-down discovery) or a list of story IDs to roll up from.
  • No LLM key — metrics, insights, and recommendations are all rule-computed, not model-generated.

Step by step

  1. Install Node.js — the runtime.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript on Node. One-time per machine.
    First run First time only, on a new machine.
  2. Clone and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the ADO client and the xlsx/report writers into node_modules.
    First run Full install, a minute or two.
    Re-run No-op once installed, unless the dependency list changed.
  3. Export the ADO target (environment variables).
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
    Why Read at startup to resolve the org/project and authenticate the read queries.
  4. Dry-run to tally bug counts on-screen.
    npm run bug:intel -- --feature-id 4001 --dry-run
# or a targeted list of stories:
npm run bug:intel -- --parent-ids "4010,4013,4060" --dry-run
    Why --dry-run walks the hierarchy and aggregates on-screen without writing files — a fast check before the full serialization.
    First run Reads every story and bug under the feature fresh.
  5. Generate the full report set.
    npm run bug:intel -- --feature-id 4001
# add a Word document too:
npm run bug:intel:word -- --feature-id 4001
    Why Drops --dry-run and serializes the report files to disk.
    Re-run No caching — every run re-queries live ADO data, so it always reflects current counts and picks up bugs filed since last run.
  6. Open the report.
    open ./outputs/reports/bug-intel/BugIntel_<timestamp>.md
    Why The .md is the at-a-glance summary; the .xlsx holds the sortable bug list and severity-by-state pivot for a deeper cut.

What you give it

--feature-id <id>
Feature ID — auto-discovers child stories and their bugs, top-down.
--parent-ids <ids>
Comma-separated story IDs to target instead of (or alongside) a feature.
--feature-name <name>
Optional report-header label, if you don't want it auto-fetched.
--word
Also serialize a .docx version.
--dry-run
On-screen tally only — no files written.
environment variables
Org/project target and the PAT.

What comes back

BugIntel_<timestamp>.json
Full structured report — totals, fix rate, per-story and per-assignee breakdowns, insights, recommendations.
BugIntel_<timestamp>.md
The same report rendered for at-a-glance reading.
BugIntel_<timestamp>.xlsx
Multi-sheet workbook: Summary, All Bugs, Per-Story, severity-by-state pivot.
BugIntel_<timestamp>.docx
Shareable Word version, only with --word.
Running it again. Nothing to warm — every run queries ADO fresh, so a second run reflects whatever changed since (newly filed, newly fixed). Schedule it to keep the report current with zero manual tallying.
Plug it into your stack. Point it at a fixed --feature-id in a nightly/weekly CI or cron job; pipe the .xlsx/.json into a dashboard, or drop the .md straight into a status channel — it's authored to be posted as-is.
