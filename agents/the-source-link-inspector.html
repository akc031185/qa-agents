The Source-Link Inspector

Verifies the assistant's cited sources actually resolve, by clicking each reference open and confirming a real blob: URL appears.

Source file: blob-reference-capture-agent.ts

When the assistant answers, it lists the documents it cited. This agent verifies those citations resolve: it confirms each cited .docx/.txt produces a working blob: URL a user could open, not just a filename with nothing behind it. Two phases — a fast API pass to send questions and extract citation IDs, then a Playwright pass that only opens conversations that actually cited something.

Why this exists

The chore it removes

The manual version: ask the assistant dozens of questions one at a time, and for each cited answer open the References panel, click each listed document, and watch whether a real file opens. Doing this by hand for a hundred questions is slow, and it's easy to lose track of which answers had solid sources and which had dead ones.

→
What you get instead

The agent runs every question, opens each answer's reference list, clicks into the .docx/.txt entries, and records the exact blob: URL each resolves to. You get one workbook: every question, its citation count, and which citations resolve to a real file.

A cited source with no real file behind it means the reader can't verify the claim — which quietly erodes trust in every answer.

What this step does

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • An app login with permission to open conversations and view the References panel.
  • A golden question list — a JSON file with an id, question text, and category per entry.
  • A one-time interactive sign-in on first run (so the agent can persist the storage-state and reuse it after).

Step by step

  1. Install Node.js — the runtime the agent runs on.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program; Node executes it. One-time setup per machine.
    First run Only needed on a fresh machine.
  2. Install the agent's dependencies, then Playwright in its sibling folder.
    cd path/to/the-agents
npm install

# the browser-clicking library lives in its own sibling folder:
cd Playwright
npm install
    Why npm install pulls the API client and the ExcelJS writer. The second install pulls in Playwright, which the agent drives to open the References panel.
    First run Downloads everything (a minute or two, longer the first time Playwright fetches its Chromium binary).
    Re-run No-op once installed.
  3. Set the target environment (environment variables).
    export APP_API_URL_DEV=https://dev.example-app.internal
export APP_API_TOKEN_DEV=your-api-token
export APP_MODEL=gpt5   # optional — which model to ask
    Why Phase 1 hits the chat API directly (fast, no browser). These variables select the environment and the token that authorizes the questions.
  4. First run: --headed so you can complete sign-in once.
    npx ts-node agents/blob-reference-capture-agent.ts \
  --env dev --golden ./questions/my-question-list.json \
  --limit 1 --headed
    Why With no cached storage-state, a visible Chromium window opens and waits for you to sign in (including any MFA step), then persists the session so future runs skip it.
    First run A browser window opens; sign in when prompted, then the run continues on its own.
  5. Real run: point it at your full question list.
    npx ts-node agents/blob-reference-capture-agent.ts \
  --env dev --golden ./questions/my-question-list.json \
  --limit 10
    Why The actual check. Phase 1 asks every question via the API and extracts citation markers; phase 2 opens only the cited answers in Chromium, clicks each reference, and records whether a blob: URL appears.
    Re-run Reuses the saved login from the first run — no browser sign-in unless the session expired.
  6. Open the report.
    open ./outputs/reports/blob-refs/BlobRefs_dev_<timestamp>.xlsx
    Why A three-tab workbook — Summary, All Results, and just the resolved citations — plus a matching JSON file with the same data.

What you give it

--env <dev|qa>
Which environment to run the questions against.
--golden <path>
The golden question list (id, text, category) to run.
--limit <n>
Run only the first N questions — handy for a quick check.
--prompts <ids>
Run only specific question ids, comma-separated.
--headed
Show the Chromium window — needed for the first sign-in.
environment variables
The API URL and token for the chosen environment.

What comes back

BlobRefs_<env>_<timestamp>.json
Every question's citations, reference count, and which ones resolved to a real file.
BlobRefs_<env>_<timestamp>.xlsx
A three-tab workbook: Summary totals, All Results, and a Blob References tab of just the resolved citations.
Running it again. No fingerprinting — each run re-asks every selected question fresh. What gets reused is the login: once the storage-state is saved, later runs (even --headless) skip signing in unless it expired.
Plug it into your stack. Point it at the same question list on a schedule (nightly, or post-deploy) so a citation quietly going dead gets caught automatically instead of during a live demo. The JSON output diffs cleanly run-over-run to spot a source that used to resolve and stopped.
