The Wait-Time Verifier

Measures the assistant's real answer latency and checks it against the 'estimated wait' range the app displays.

Source file: time-range-verification-agent.ts

While the assistant is thinking, the app shows a range like 'Wait time: about 5 to 10 seconds.' This agent verifies that promise: it fires questions across a size spectrum, scrapes the displayed range, times the actual latency to a tenth of a second via Playwright, and flags any estimate the real wait blew past.

Why this exists

The chore it removes

The manual version: sit with a stopwatch, type a question, read the estimate, start timing on Enter, stop when the answer appears. Repeating that across short questions, long essay prompts, and everything between is tedious and imprecise — human timing is off by seconds, and nobody wants to babysit fifty prompts by hand.

→
What you get instead

The agent fires a whole library of differently-sized questions, scrapes the on-screen estimate for each, times the real wait to the tenth of a second, and marks whether the actual latency fell inside the promised range. It also captures screenshots throughout, as evidence of what the screen showed at each moment.

If the app keeps promising '5 seconds' but takes 40, users lose patience and trust; catching that gap early keeps the estimate believable.

What this step does

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • An app login — the agent navigates straight to the app and only stops for sign-in on an actual redirect to a login page.
  • No content prep: a built-in library of sample questions ships with the agent, short to very-long, so it runs out of the box.

Step by step

  1. Install Node.js — the runtime the agent runs on.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program; Node executes it. One-time setup per machine.
    First run Only needed on a fresh machine.
  2. Install the agent's dependencies, then Playwright in its sibling folder.
    cd path/to/the-agents
npm install

# the browser-clicking library lives in its own sibling folder:
cd Playwright
npm install
    Why The root install pulls the ExcelJS writer and the tsx runner. The second pulls in Playwright — which opens the app, types the question, and watches the screen.
    First run Downloads everything (a minute or two, longer the first time Playwright fetches its Chromium binary).
    Re-run No-op once installed.
  3. (Optional) set an SSO password if your login uses one.
    export SSO_PASSWORD=your-password
    Why The agent goes straight to the app; on a redirect to a company SSO page it tries this password automatically. Leave it unset and sign in by hand the first time — either way the storage-state gets saved for next time.
  4. Run against the target environment.
    npx tsx agents/time-range-verification-agent.ts --env dev
    Why The actual run. A visible Chromium window opens, asks each library question in turn, scrapes the on-screen estimate, times the real latency to a tenth of a second, and screenshots throughout.
    First run A browser opens; sign in when prompted (or it uses the password above). A full run can take a while — the library includes deliberately slow, very-long-response questions.
    Re-run Add --headless once signed in, so it runs invisibly: npx tsx agents/time-range-verification-agent.ts --env dev --headless.
  5. Open the report.
    open ./outputs/reports/wait-time/WaitTime_dev_<timestamp>.xlsx
    Why A color-coded workbook — green for latencies inside the promised range, red for outside — grouped by category, plus a screenshots tab and a full screenshot folder.

What you give it

--env <dev|qa>
Which environment's URL to open.
--headless
Run invisibly in the background instead of showing the browser window.
--prompts "A|B|C"
Run your own pipe-separated question list instead of the built-in library.
--offset / --limit / --worker-id
Shard the library across parallel runs — useful for a big batch.
environment variables
An optional SSO password, only if your login has one.

What comes back

WaitTime_<env>_<timestamp>.json
Every question's displayed wait-time range, the two measured times, and the inside/outside verdict.
WaitTime_<env>_<timestamp>.xlsx
A color-coded, category-grouped report with a per-category accuracy percentage and a screenshots tab.
screenshots_<env>_<timestamp>/
A full folder of screenshots — the prompt, the wait-time note, the processing state every few seconds, and the finished answer.
Running it again. Every run times every question fresh — nothing is cached but the login session. It's built to shard: run four workers in parallel, each with a different --offset/--limit/--worker-id, and merge the reports after.
Plug it into your stack. Run it nightly (or post-deploy) against QA and watch the per-category accuracy over time. An estimate that used to hold and now doesn't is exactly the quiet regression this catches before users notice.
