Deciding what to test

The Test-Case Reviewer

Splits a test-results spreadsheet into a passed-verified acceptance-criteria doc and a review sheet of everything needing a human ruling.

Source file: tc-review-agent.ts

Partitions a round of test results into two work-products with different follow-up. Passing rows become a clean Given/When/Then acceptance-criteria document. Failures and untested rows become a review sheet — expected vs actual, tester comment preserved — with decision tick-boxes for the lead to rule on each.

Why this exists

The chore it removes

After execution, someone sorts the results spreadsheet by hand: passes get written up as confirmed behavior; every failure or skip has to be summarized — expected, actual, tester note — and put in front of the scrum master to rule 'real bug or bad test?'. Across many tabs it's tedious and the write-ups come out inconsistent.

→
What you get instead

The agent reads the workbook and emits two documents. One is an acceptance-criteria document built only from PASS rows, in Given/When/Then form with duplicates merged. The other is a review sheet listing every non-passing test — expected result, actual result, tester comment verbatim — with tick-boxes for 'Valid Bug', 'Invalid Test', or 'Needs More Info'.

Every failed or skipped test gets an explicit human ruling instead of slipping through the gap between 'passed' and 'forgotten'.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • A results workbook — one tab per feature, with columns for scenario, expected result, actual result, status, and comments (order can vary; columns are resolved by header text).
  • A Google Gemini API key for the merged, polished write-up; without it the agent degrades to a deterministic rule-based version built straight from the rows.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program executed under Node. One-time install per machine.
    First run First time on a new machine only.
  2. Clone the code and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install resolves the agent's dependencies — the ExcelJS reader, the docx writer, and the Gemini client — into node_modules.
    First run Downloads everything (a minute or two).
    Re-run No-op unless the dependency set changed.
  3. Set the LLM key (optional).
    export GOOGLE_API_KEY=your-gemini-key   # optional
    Why Read at startup. If unset, the agent still runs — it degrades to the deterministic rule-based write-up with no model wordsmithing.
  4. Dry-run first — inspect the workbook without spending LLM calls.
    npx tsx agents/tc-review-agent.ts --excel ./inputs/results.xlsx --dry-run
    Why --dry-run reads every tab and prints passed vs review counts per feature — confirms the columns resolved correctly before the real run.
    First run Prints counts only — no documents written.
  5. Run for real; add --word for the docx files.
    npx tsx agents/tc-review-agent.ts --excel ./inputs/results.xlsx --word
    Why Drop --dry-run. Builds two documents: an acceptance-criteria doc from the passes, and a review sheet — with tick-boxes — for everything else.
    First run Partitions each tab into passed/non-passed, sends each pile to the LLM, and writes both documents.
    Re-run Recomputes fresh from the workbook's current contents — re-run after the next execution round to pick up new results.
  6. Open the two documents.
    open ./outputs/reports/tc-spec/TC_AC_Document_*.md
open ./outputs/reports/tc-spec/TC_Review_Document_*.md
    Why The AC document is confirmed behavior, ready to file. The review document goes to the lead — each entry has tick-boxes for 'Valid Bug', 'Invalid Test', or 'Needs More Info'.

What you give it

--excel <path>
The results workbook, one tab per feature. Falls back to a standard inputs folder if omitted.
--word / --dry-run
--word also emits the Word documents; --dry-run prints the pass/review counts and stops.

What comes back

TC_AC_Document_<timestamp>.md / .json / .docx
A Given/When/Then acceptance-criteria document from the passing tests only — duplicates merged.
TC_Review_Document_<timestamp>.md / .json / .docx
One entry per failed/skipped test — expected vs actual, tester comments verbatim, and tick-boxes for the lead's ruling.
Running it again. Stateless — each run reads the workbook's current state and rebuilds both documents from scratch. Re-run after every execution round or whenever the results sheet updates; treat the new files as the current snapshot.
Plug it into your stack. Route the AC document to whoever maintains the feature's official acceptance criteria. Route the review document straight to the team lead or scrum master for a ruling — nothing should sit between 'tested' and 'decided' for long.
