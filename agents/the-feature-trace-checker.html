The Feature-Trace Checker

Drives the app in a real browser, enables the function-call trace toggle, sends a prompt, and asserts the answer, its trace, and the saved conversation all appear.

Source file: function-call-share-agent.ts

Runs the actual app in a headless-or-headed Chromium session via Playwright, exactly as a user would — clicking, typing, waiting. It first flips the settings toggle that surfaces the app's function-call trace, sends a prompt, waits for the streamed answer to fully settle, then asserts the trace panel rendered and the conversation persisted to history.

Why this exists

The chore it removes

Checking this by hand is tedious and easy to rush: open settings, find the toggle, set it to Yes, save, start a new chat, type the prompt, then — the slow part — watch until the streamed answer stops growing (minutes), squint for the function-call panel, note the title, go home, and scroll the list to confirm the conversation saved. Across many prompts it's mind-numbing, and a distracted tester calls a half-streamed answer 'done'.

→
What you get instead

The agent runs the full click-by-click routine and, critically, waits for the answer to truly finish streaming before asserting. Per prompt it records answer length, whether the trace panel appeared, the conversation title, and whether the conversation showed up in the saved list — then returns a clean pass/fail summary.

A human watching a screen eventually blinks, gets bored, or calls a still-streaming answer finished — the agent never does, so slow or missing function-call traces get caught instead of waved through.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Playwright installed with its Chromium binary downloaded (npx playwright install).
  • A real account for the app — the first run pauses up to 3 minutes for a one-time manual sign-in, then reuses the saved storage-state session.
  • The app must expose a settings toggle that surfaces its function-call trace — the agent finds and enables it for you.

Step by step

  1. Install Node.js — the runtime the agent runs on.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program; Node executes it. Install once per machine.
    First run Only needed on a fresh machine.
  2. Install dependencies and the Chromium binary.
    cd path/to/the-agents
npm install
npx playwright install   # one-time: downloads the actual browser binary
    Why npm install pulls the agent's dependencies; playwright install downloads the Chromium binary the agent drives — a one-time download, not a per-run step.
    First run Downloads Chromium (a few minutes on a slow connection).
    Re-run Skipped entirely once the binary is present.
  3. Run once headed to sign in.
    npx tsx agents/function-call-share-agent.ts --env dev \
  --prompt "What does the app do for expense reports?"
    Why Omitting --headless opens a visible Chromium window. The first run pauses on the SSO screen for manual login, then persists the storage-state session so it never asks again.
    First run Pauses up to 3 minutes for manual sign-in, then saves the session to a local file.
    Re-run Signs in silently from the saved session — no pause, unless it expired.
  4. Run for real on a prompt list, headless if you like.
    npx tsx agents/function-call-share-agent.ts --env dev \
  --input prompts.txt --headless
    Why --input reads one prompt per line and runs the full click-type-wait-assert routine for each. --headless drops the window once you trust it — useful in CI.
  5. Open the report.
    open ./outputs/reports/function-call-shares/FuncCallShare_dev_<timestamp>.json
    Why Per prompt, records whether the trace appeared, the answer's word count, the conversation title, and whether it persisted to the saved-conversations list.

What you give it

--prompt "..." (repeatable) or --input <file>
One or more prompts to send, typed directly or read one-per-line from a text file.
--env dev|qa
Which environment's app instance to drive in the browser.
--headless
Run with no visible window (default is headed, so you can watch and sign in the first time).

What comes back

console log
A numbered step trace per prompt as it happens — new chat, prompt sent, response complete, trace checked, saved-list checked.
FuncCallShare_<env>_<timestamp>.json
One pass/fail record per prompt — answer word count, whether the function-call trace rendered, the conversation title, and whether it persisted to the saved list.
Running it again. Sign-in is cached via the storage-state file, so re-runs skip straight to sending prompts. Everything else is fully live — each run starts a brand-new chat per prompt, so re-running the same list produces a fresh batch to check, not a replay.
Plug it into your stack. Built for a regression suite: point it at a fixed prompt list after any change that could touch the trace feature or the save-to-history path, run it headless in CI, and fail the build on any 'not found in panel' or missing-trace result — exactly the intermittent bug a rushed human waves through because they blinked at the wrong moment.
