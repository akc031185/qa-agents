Finding & reporting problems

The Bug Filer

Files a typed, deduplicated ADO Bug work item per test failure — title, repro steps, severity, screenshot, parent link — in one pass.

Source file: ado-bug-agent.ts

Consumes a TestFailure[] from your runner and files each failure as a fully-populated Azure DevOps Bug via the REST API. Every field is set — title, description table, Microsoft.VSTS.TCM.ReproSteps, severity, priority, tags — the screenshot is attached, and the bug is linked under its parent user story. Idempotent: it searches for an existing open bug before creating.

Why this exists

The chore it removes

Manual triage means opening the tracker and hand-keying each failure into a new ticket: title, error, repro steps, severity, browser, screenshot, parent link. Across a dozen failures it's slow, and fatigue produces vague titles, missing screenshots, and duplicate filings.

→
What you get instead

One consistently-structured Bug work item per failure, filed the moment it lands — identical field layout every time, no duplicates, no blank fields. Severity and priority are assigned by deterministic keyword rules, so the same failure always grades the same way.

A clearly-written bug filed instantly gets fixed sooner. A vague or forgotten one regresses to production. Deterministic filing removes the human variance that lets that happen.

What this step does

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • An Azure DevOps org/project and a PAT with work-item write (create Bug) scope.
  • A TestFailure[] JSON array from your runner — testCase, browser, error, optional screenshot path.
  • No LLM key — severity and priority are deterministic keyword rules, not a model.

Step by step

  1. Install Node.js — the runtime.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript on Node. One-time per machine.
    First run First time only, on a new machine.
  2. Clone and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the ADO client and helpers into node_modules.
    First run Full install, a minute or two.
    Re-run No-op once installed, unless the dependency list changed.
  3. Export the ADO target (environment variables).
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
export ADO_AREA_PATH="My Project\\MyTeam"   # optional
    Why Read at startup to resolve the org/project and authenticate. Swap them to retarget a different project.
  4. Dry-run to preview the create/skip decisions.
    npm run ado:bugs -- \
  --story 4001 \
  --failures '[{"testCase":"login-smoke","browser":"chromium","error":"Timed out waiting for the Sign In button"}]' \
  --dry-run
    Why --dry-run runs the full WIQL-search and decide flow but suppresses the write — validates your --failures JSON shape first.
  5. Run for real.
    npm run ado:bugs -- \
  --story 4001 \
  --failures '[{"testCase":"login-smoke","browser":"chromium","error":"Timed out waiting for the Sign In button"}]'
    Why Drops --dry-run and files one Bug per failure, severity/priority auto-graded.
    First run Files a net-new Bug for every failure with no matching open bug.
    Re-run Same failure hits the WIQL dedup gate: skipped, or — with --update-existing — a timestamped comment instead of a duplicate.
  6. Open the filed bug.
    # the agent prints each ticket's link to the console, e.g.:
# Created: #6002  https://dev.azure.com/my-org/My%20Project/_workitems/edit/6002
    Why No local artifact — the Bug work item on ADO is the output; the console prints its url.

What you give it

--failures <json>
TestFailure[] JSON — testCase, browser, error, optional screenshot path.
--story <id>
Parent user story ID to hierarchy-link every new bug under.
--dry-run
Run the search/decide flow but suppress the write.
--update-existing
Comment on a dedup match instead of skipping it.
environment variables
Org/project target and the PAT.

What comes back

Bug work items
Created (or commented-on) directly in ADO — no local files written.
console summary
created / updated / skipped / errored counts, plus each new bug's url.
Running it again. Idempotent by construction: each failure hits the WIQL dedup gate (open Bug whose title CONTAINS the test case and browser) before any write, so a repeat failure never becomes a duplicate — it's skipped, or appended as a comment under --update-existing.
Plug it into your stack. Wire it as the terminal step of a CI test job: emit the runner's failures as JSON, pipe into --failures, set --story from the build's linked feature. Add --update-existing on nightly/regression runs so a flaky failure accretes history on one bug instead of piling up duplicates.
