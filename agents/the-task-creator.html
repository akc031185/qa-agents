Keeping the project tracker up to date

The Task Creator

Batch-creates ADO Task work items from an in-file plan — each fully populated and parented under its user story via a Hierarchy link.

Source file: create-ado-tasks.ts

When a batch of work is planned — each item with title, description, owner, and acceptance criteria — someone still has to key it into ADO. This agent does that data entry: it POSTs each Task fully populated and parents it under the correct user story via a Hierarchy-Reverse link, so nothing is orphaned.

Why this exists

The chore it removes

Creating a dozen tasks by hand is repetitive and error-prone. Per task: open a blank form, paste title, description, and acceptance criteria, set priority, add tags, then link the parent — sometimes two parents. Twelve times over, it's easy to drop a link, mistype a tag, or skip the acceptance criteria entirely.

→
What you get instead

The agent holds the plan and creates each Task in one run — title, description, acceptance criteria, priority, and tags all set. It links each to its first parent during creation, and PATCHes extra Hierarchy-Reverse links for any task with multiple parents. It closes with a summary table of what got created and where it landed.

Consistent, fully-linked tasks mean the agreed plan lands in ADO exactly as intended, with nothing dropped.

What this step does

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Azure DevOps access and a PAT scoped to create work items.
  • The planned batch written out — title, description, acceptance criteria, priority, tags, and parent story ID(s) per item.

Step by step

  1. Install Node.js — the engine that runs the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript run under Node — a one-time per-machine install.
    First run One-time setup per machine.
  2. Clone the agent and install its dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the one dependency this script needs to talk to the ADO REST API.
    First run Cold install — a minute or two.
    Re-run No-op unless package.json changed.
  3. Set the write PAT (env var).
    export ADO_PAT_WRITE=your-access-token
    Why The one secret the script needs. Unlike the other agents, this one hard-codes its target org/project and the task plan in the source file rather than taking flags — see the next step.
  4. Edit the source and fill in your batch.
    # in agents/create-ado-tasks.ts, near the top:
const ADO_ORGANIZATION = 'my-org';
const ADO_PROJECT = 'My Project';

// further down, replace the `tasks` array with your own planned batch:
const tasks: TaskDefinition[] = [
  { id: 'T1', title: '...', assignedTo: '...', parentUS: ['4001'], description: '...', acceptanceCriteria: '...', tags: '...', priority: 'High' },
  // ...
];
    Why This script targets one specific batch, not a generic importer — the org/project and the tasks array are constants in the file. Editing them here is this agent's 'input' step.
  5. Run it and read the printed summary table.
    npm run ado:tasks
    Why Creates every task in your tasks array, links each to its parent(s), and prints a table of what was created and where it landed — plus each new item's URL.
    First run Creates the whole batch from scratch.
    Re-run Non-idempotent — re-running creates a duplicate batch. Re-run only after clearing or editing the tasks array.

What you give it

the `tasks` array (in-file)
Each planned item's title, description, acceptance criteria, priority, tags, and one or more parent story IDs.
ADO_ORGANIZATION / ADO_PROJECT (in-file constants)
Which ADO org/project to create the tasks in.
ADO_PAT_WRITE (environment variable)
The PAT authorizing the script to create work items.

What comes back

new Tasks in ADO
Each fully populated and nested under its parent story (or stories) via Hierarchy-Reverse.
console summary table
Task, new work item ID, parent, and status (Created/Failed) for every item, plus each URL.
Running it again. Non-idempotent — each run creates brand-new tasks with no memory of prior runs, so re-running the same tasks array duplicates the whole batch. Clear the array (or comment out already-created items) before re-running.
Plug it into your stack. Treat this as a one-off migration script per planning batch, not a scheduled service — copy it, swap in the next batch's tasks, run once, then set it aside until the next planning round.

Populating the Task fields

When it runs
Once per planned task, first.
Takes in
A task's title, description, acceptance criteria, priority, and tags.
Shows out
A single POST that creates the Task, fully populated.
2 / 4

Linking the first parent

When it runs
Inline in the same POST that creates the task.
Takes in
The task's primary parent story ID.
Shows out
The new Task appears nested under that story in ADO.
3 / 4

PATCHing extra parents

When it runs
Right after creation, only for tasks with more than one parent.
Takes in
The new task's ID and each additional parent ID.
Shows out
One more Hierarchy-Reverse link per extra parent, each confirmed independently.
4 / 4

Printing the summary

When it runs
After every task in the batch has been attempted.
Takes in
Each task's outcome — created or failed — and its links.
Shows out
A markdown summary table (task, new work item ID, parent, status) plus each item's URL.
