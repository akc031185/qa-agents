Turning results into reports people read

The Scorecard Publisher

Merges two disjoint eval pipelines — guardrail/contract probes and answer-quality grading — into one scorecard with a single Pass/Warning/Fail verdict and prioritized fixes.

Source file: eval-report-agent.ts

Two eval pipelines produce differently-shaped result files: contract/probe runs that assert the assistant obeys its rules and refuses bad requests, and quality-grading runs that score answer quality. This agent discovers the newest file from each, normalizes both into one summary (pass rate, verdict counts, gate failures, average scores), computes an overall verdict under fixed precedence rules, and emits a report with ranked, actionable recommendations.

Why this exists

The chore it removes

The manual path: open several raw result JSONs, read numbers out of each, decide by hand whether the whole run passes, and hand-write a summary for stakeholders who won't read raw data. Tedious, and easy to miss a critical failure buried in one pile.

→
What you get instead

One scorecard that aggregates both pipelines, decides the overall verdict by explicit precedence, and lists — ranked by severity — what to fix and why.

A single PII leak or a hallucinated answer can sink trust in the whole assistant. Surfacing gate failures first, and letting them override otherwise-green scores, is what keeps a launch honest.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • At least one upstream pipeline already run: the contract/probe checks and/or the quality-grading run.
  • Nothing else to configure — this agent only reads result files other agents wrote; it never calls the assistant or an LLM judge itself.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program; Node executes it. One-time per machine.
    First run Needed only the first time on a new machine.
  2. Clone the agents and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the agent's dependencies — the .xlsx writer and the .docx writer — into node_modules.
    First run Downloads everything (a minute or two).
    Re-run No-op unless the dependency list changed.
  3. Ensure at least one upstream pipeline has produced a result file.
    # Contract/probe checks:
npm run eval:contract:teacher && npm run eval:probe:teacher

# Quality grading:
npm run eval:user:run
    Why This agent tests nothing itself — it merges whatever the two upstream pipelines most recently wrote. With neither ever run, there is nothing to merge; it reports that and exits.
  4. Generate the scorecard.
    npm run eval:report -- --word --include-all
    Why Discovers the newest file from each pipeline, normalizes and merges them, applies the fixed pass/warning/fail precedence, and writes the recommendations. --word adds a .docx; --include-all includes every prompt-level detail, not just the summary.
    First run Reads whatever the latest runs of both pipelines produced.
    Re-run Re-run whenever either pipeline writes a new result file — it always picks the newest by mtime automatically.
  5. Open the generated scorecard.
    open outputs/eval/reports/eval-report-<timestamp>.md
    Why The .md is the scorecard — the overall PASS/WARNING/FAIL verdict, a section per pipeline, and the ranked list of what to fix and why.

What you give it

--system-only | --user-only
Scope the scorecard to only the contract/probe results, or only the quality results (default: both).
--word, --excel, --include-all
Also emit a .docx, a .xlsx, or include every prompt-level detail rather than just the summary.
--filter-verdict <PASS,WARNING,FAIL>
Include only prompts whose individual verdict is in this comma-separated set.
--system-path, --user-path, --comparison-path, --output <dir>
Override which specific result file(s) to read, or the output directory, instead of auto-discovering the newest.

What comes back

eval-report-<timestamp>.json / .md
The structured and human-readable scorecard — overall verdict, per-pipeline summary, and ranked recommendations.
eval-report-<timestamp>.docx / .xlsx (optional)
A .docx and/or .xlsx view, emitted only with --word or --excel.
Running it again. Nothing to fingerprint — every run re-reads whichever result files have the newest mtime at that moment. Run it again right after a fresh probe or grading run and the scorecard reflects the latest numbers; nothing needs clearing first.
Plug it into your stack. Chain it as the final CI step after the full eval pipeline (contract probes, then quality grading, then this), so every model or prompt change emits a fresh go/no-go scorecard with no hand-assembly.

Discover latest result files

When it runs
First, at agent startup.
Takes in
The two output directories — one holding contract/probe runs, one holding quality-grading runs.
Shows out
The newest file in each directory, selected by mtimeMs (via discoverLatestFile()).
2 / 5

Load and normalize both pipelines

When it runs
Immediately after the latest files are located.
Takes in
The two raw result files, shaped differently because they come from different pipelines.
Shows out
One EvalReportSummary shape — pass rate, verdict counts, gate failures, average scores — independent of source pipeline (via loadSystemResults(), loadUserResults(), and buildSummary()).
3 / 5

Compute overall verdict

When it runs
Once both pipelines are normalized into the summary.
Takes in
The merged summary.
Shows out
One overall PASS/WARNING/FAIL, decided by fixed precedence — any PII or safety gate failure forces FAIL regardless of other scores (via computeOverallVerdict()).
4 / 5

Localize weak spots

When it runs
After the overall verdict is set.
Takes in
Every prompt-level result across the contract probes and the quality dimensions.
Shows out
A severity-ranked list of the worst gates, metrics, and prompt IDs, each rendered as a recommendation with a concrete remediation (via buildRecommendations()).
5 / 5

Serialize the scorecard

When it runs
Last, once summary and recommendations are final.
Takes in
The merged summary plus the recommendation list.
Shows out
A JSON file for downstream tooling, a Markdown report, and — on request — a .docx and .xlsx for stakeholders (via generateReportMarkdown(), generateWordDoc(), and generateExcel()).
