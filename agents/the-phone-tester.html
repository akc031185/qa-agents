The Phone Tester

Runs the existing Playwright suite against emulated iOS/Android device profiles and, per failure, emits numbered manual-repro steps plus a device-simulator link.

Source file: mobile-testing-agent.ts

Executes the app's Playwright tests against the mobile-chrome (Android) and mobile-safari (iOS) projects, ingests a step-level results file to pin the exact step that broke, then rewrites each failure as numbered manual-repro instructions — open simulator, navigate to the app URL, log in, walk the steps, expected vs. actual — with a ready-made simulator link for the device.

Why this exists

The chore it removes

Real-device testing is fiddly: source the devices, log in, tap the same steps, and on a break, hand-write what you did so a dev can repeat it. Doing that on both iOS and Android, per test, with clear repro notes each time, burns hours.

→
What you get instead

A pass/fail scoreboard per device profile and, per failure, a numbered repro recipe — device, browser, taps, expected, actual — with a simulator link to reproduce it live.

An unreproducible failure gets argued about and ignored; a failure with numbered steps and a device link gets fixed.

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • The target app running at a reachable URL (dev or QA).
  • An existing Playwright test suite — this agent runs those tests against mobile device profiles, it doesn't author new ones.
  • ~10 min on first run: npx playwright install downloads the Chromium and WebKit engines before anything runs.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program executed by Node. One-time install per machine.
    First run Only needed once per new machine.
  2. Install dependencies — once for the agent, once for the Playwright package it drives.
    cd path/to/the-agents
npm install

cd Playwright
npm install
npx playwright install   # downloads the actual Chromium + WebKit browser engines
    Why The agent lives in the project root; the test-execution layer lives in a sibling Playwright dir with its own deps. npx playwright install fetches the engines the tests run in — Chromium for the Android profile, WebKit for iOS — not bundled with the npm package.
    First run Downloads deps plus the browser engines — the slow part (5-10 min).
    Re-run No-op once installed, unless a dependency or browser version changed.
  3. Set the target URL.
    export APP_URL=https://your-app-url/home
    Why APP_URL is the live app the tests open on each device profile. Unset, they fall back to a built-in default that won't be your app.
  4. Run it.
    npm run mobile:test -- --word
    Why The full run: executes the existing suite against the Android (mobile-chrome) and iOS (mobile-safari) profiles with step-level recording, then writes the scoreboard. --word additionally emits a .docx.
    First run Runs every test against both device profiles from scratch.
    Re-run --device android or --device ios scopes to one profile; --test-file <path> re-runs a single test while chasing one failure.
  5. Open the generated report.
    open outputs/mobile/reports/mobile-report-<timestamp>.md
    Why The .md holds the per-device pass/fail scoreboard and, under each failure, numbered manual-repro steps plus a device simulator deep link.

What you give it

APP_URL (environment variable)
URL of the running app the tests open.
--device android | ios | all
Device profile(s) to run against; defaults to both.
--test-file <path>, --simulator <provider>, --headed, --include-passed, --word
Flags to scope to one test file, pick the simulator provider to link to, run headed, include passing tests in the report, or emit a .docx.

What comes back

mobile-report-<timestamp>.json / .md
Machine-readable and rendered pass/fail scoreboard, with numbered manual-repro steps under every failure.
mobile-report-<timestamp>.docx (optional)
.docx of the same report; emitted only with --word.
step-results-latest.json
The step-level record written during the run — the source the agent parses to pin exactly which step broke.
Running it again. --device android or --device ios scopes the run to the profile you're chasing a fix on — far faster than a both-profiles run. Every run is a fresh execution; no fingerprinting here, since app behavior (not documents) is what's being exercised.
Plug it into your stack. Add the --device all run to CI on every pull request; treat a check that fails on one profile but passes on the other as a platform-specific bug, not a flake.
