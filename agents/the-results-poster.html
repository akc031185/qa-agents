Keeping the project tracker up to date

The Results Poster

Derives each test case's Passed/Failed outcome from the story's ADO state — QA task closure and bug links — then posts the results to a test run.

Source file: ado-test-results-agent.ts

After execution, someone has to record Passed/Failed on every test point. This agent infers the outcome from signals already in ADO — whether the QA execution Task is Closed and whether bugs are linked to specific test cases — then posts the verdicts automatically via a test run.

Why this exists

The chore it removes

A tester finishes a feature, then updates the tracker one test point at a time: open each, decide pass or fail, recall which bug maps to which test case, and click through several screens to record it. Across dozens of test cases and many features it's an afternoon of clicking — and easy to mismark or skip a few.

→
What you get instead

The agent reads each story and applies three deterministic rules. QA task Closed with no bugs → every test case Passed. Bugs linked to specific test cases → exactly those Failed, the rest Passed. QA task not Closed → skip and leave a reminder comment instead of guessing. It then posts all outcomes to a single test run.

An accurate results board is what signals a feature is genuinely shippable — a rushed or wrong outcome can green-light something that isn't.

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Azure DevOps Test Plans access and a PAT scoped to write test results.
  • The stories under test must have their QA execution Task Closed, and any bugs filed must be TestedBy-linked to the test case they came from — otherwise the agent skips and queues a reminder instead of guessing.

Step by step

  1. Install Node.js — the engine that runs the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript run under Node — a one-time per-machine install.
    First run One-time setup per machine.
  2. Clone the agent and install its dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the ADO client and xlsx reader into node_modules.
    First run Cold install — a minute or two.
    Re-run No-op unless package.json changed.
  3. Set the target org, project, and PAT (env vars).
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
    Why Read at startup: which ADO org/project to hit and the PAT that authorizes writing results.
  4. Preview outcomes with --dry-run.
    npm run ado:results:update -- --plan-id 12345 --suite-id 67890 --stories 3101,3102 --dry-run
    Why --dry-run runs the same analysis and prints exactly what it would post — Passed/Failed/skipped, story by story — without creating a run. Review before writing.
    First run Analyzes each story fresh.
  5. Post the outcomes for real.
    npm run ado:results:update -- --plan-id 12345 --suite-id 67890 --stories 3101,3102
    Why Same analysis, but now it creates a test run, PATCHes every result, and completes the run.
    Re-run Non-idempotent — each invocation creates a new test run, so re-running the same stories posts a second, redundant run. Re-run only once the underlying bug links or QA task state actually changed.
  6. Check current status any time, read-only.
    npm run ado:results:status -- --plan-id 12345 --suite-id 67890
    Why Never writes — tallies each test point's lastResultOutcome, handy for a quick 'are we there yet' check.

What you give it

--plan-id <id> --suite-id <id>
Which Test Plan and suite to post results into.
--stories <ids> / --feature-id <id> / --from-excel <path>
Which stories to analyze — explicit list, parent feature, or a spreadsheet column.
--test-case <id> --outcome <value>
Manual override to set a single test case's outcome directly.
--status
Read-only: print the current outcome tally without posting.

What comes back

a new test run in ADO
Created, PATCHed result-by-result with Passed/Failed plus a reason comment, then completed — nothing saved locally.
reminder comments
Posted on the QA task (if not Closed) or on a bug (if not linked to a test case), so nothing silently falls through.
Running it again. Non-idempotent by design — every successful post creates a fresh test run, so re-running against unchanged data yields a second, redundant run. Re-run only after the QA task state or a bug's links actually changed.
Plug it into your stack. Trigger this right after the QA execution Task is Closed so the results board updates automatically the moment execution is done, instead of waiting for someone to click through it by hand.
