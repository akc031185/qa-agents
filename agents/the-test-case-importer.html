Keeping the project tracker up to date

The Test-Case Importer

Bulk-creates ADO test cases from an xlsx of steps — grouping rows, encoding steps, linking to the parent story — and files them into a suite.

Source file: ado-testcase-creator-agent.ts

Testers draft in a spreadsheet — one row per step, with action and expected result. This agent reads it with xlsx, groups rows into test cases by title, and creates each as a structured ADO Test Case work item: steps, priority, TestedBy link, and owner all set. It emits a before/after mapping of every row to its new work item ID.

Why this exists

The chore it removes

Hand-copying tests from a spreadsheet into ADO is mind-numbing. Per test case: open a blank form, type the title, add each step and expected result one by one, set priority, link it to the story, save — then repeat dozens of times. Slow, and skipped steps or wrong links creep in as attention drifts.

→
What you get instead

The agent reads the whole spreadsheet at once, groups rows into complete test cases, and creates each fully formed — every step, expected results, priority, TestedBy link to the parent story, and owner. It writes before/after mapping spreadsheets tracing each row to its new work item ID, and can add the batch straight into a suite.

A hundred test cases into ADO in minutes instead of a day means testers spend their time testing, not typing into forms.

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Azure DevOps Test Plans access and a PAT scoped to create test cases.
  • An xlsx of drafted tests: one row per step, columns Title, Step #, Action, Expected Result, Priority, and Story ID.

Step by step

  1. Install Node.js — the engine that runs the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript run under Node — a one-time per-machine install.
    First run One-time setup per machine.
  2. Clone the agent and install its dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the xlsx reader and ADO client into node_modules.
    First run Cold install — a minute or two.
    Re-run No-op unless package.json changed.
  3. Set the target org, project, and PAT (env vars).
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
    Why Read at startup: which ADO org/project to create the test cases in and the PAT that authorizes it.
  4. Preview the grouping with --dry-run.
    npm run ado:testcases:create -- --input ./drafted-tests.xlsx --dry-run
    Why --dry-run groups rows into test cases and lists each one's title, step count, and parent story — nothing written to ADO. Verify the grouping before committing.
    First run Parses the whole xlsx fresh.
  5. Create the test cases, optionally adding them to a suite.
    npm run ado:testcases:create -- --input ./drafted-tests.xlsx --plan-id 1101 --suite-id 1102
    Why Same grouping, but now each test case is created in ADO — steps, priority, and TestedBy link in place — and, because --plan-id/--suite-id were given, added to that suite in the same run.
    Re-run Non-idempotent — re-running the same xlsx creates a duplicate batch. Re-run only on a fresh or updated spreadsheet.
  6. Open the before/after mapping workbooks.
    open ./ADO_Steps_Mapping_<timestamp>.xlsx
open ./ADO_Steps_Mapping_WithIDs_<timestamp>.xlsx
    Why Both land next to your input file. The first is a snapshot of what was about to be created; the second stamps the real work item ID and URL onto every row, so any step traces back to what it became.

What you give it

--input <xlsx>
xlsx with Title, Step #, Action, Expected Result, Priority, and Story ID columns — one row per step.
--plan-id <id> --suite-id <id>
Optional: add the newly created test cases to this suite.
--stories <ids>
Optional: only create the test cases belonging to these parent stories.
--dry-run
Preview the grouped test cases without creating anything.

What comes back

ADO_Steps_Mapping_<timestamp>.xlsx
A 'before' snapshot of every test case about to be created, saved next to the input file.
ADO_Steps_Mapping_WithIDs_<timestamp>.xlsx
The same rows, now stamped with each test case's new work item ID and URL.
new test cases in ADO
Each fully built — steps, priority, and a TestedBy link to its parent story.
Running it again. Non-idempotent — every run creates brand-new work items, so re-running an unchanged xlsx duplicates the batch. Re-run only after editing the spreadsheet, and use --stories to scope a re-run to just the changed rows.
Plug it into your stack. Hand testers the before/after mapping as a receipt — the WithIDs file is the audit trail proving which drafted row became which live test case, and it's the natural input to the results-poster once those cases are executed.
