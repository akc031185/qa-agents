Grading the AI assistant's answers

The Rule Tester

Fires each generated probe at the live assistant and reports, with evidence, whether it actually enforces its own system-prompt contract.

Source file: contract-probe-runner-agent.ts

A contract of clauses and probes is only half the job — the probes have to run against the real assistant. This agent loads the probe file, sends each prompt to the live API, runs deterministic checks on the reply, and emits a compliance scorecard showing which clauses held and which broke.

Why this exists

The chore it removes

By hand, a tester pastes each probe into the assistant, reads the reply, and decides whether it complied — did it refuse the dangerous request, avoid echoing the fake email, stay in role. Judging is inverted for safety probes: a blunt refusal is the correct answer, the opposite of a normal test. Doing dozens consistently, and timing each, is tedious and error-prone.

→
What you get instead

Every probe fires at the assistant automatically, each reply judged by the right rule — including negative tests where a refusal is a PASS — plus latency and a clean pass-rate scorecard.

This is the proof step: it demonstrates, with evidence, whether the assistant keeps its safety and behavior contract before real users probe it.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node >= 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • The -probes.json file The Rulebook Extractor emitted.
  • The assistant API's base URL and access token, so the agent can fire the probes live.
  • (Optional) The toolkit's local checker service running, for an LLM-judged second opinion on tone and helpfulness alongside the deterministic checks.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program executed by Node. One-time install per machine.
    First run Needed only the first time on a new machine.
  2. Clone the agent code and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the small set of helper libraries into node_modules.
    First run Downloads everything (a minute or two).
    Re-run No-op once installed, unless the dependency list changed.
  3. Point it at the assistant (env vars).
    export APP_API_URL=https://your-assistant-host.example.com
export APP_API_TOKEN=your-access-token
export APP_MODEL=gpt4o
    Why Read at startup: which assistant to test and the token that authorizes it. Nothing is hard-coded — swap these to retarget environments.
  4. Rehearse the run with --dry-run first — no live calls.
    npm run eval:probe:dry -- --contract outputs/eval/contract-teacher-<hash>-probes.json
    Why --dry-run exercises every check and the full report format on simulated replies, so you confirm the right file and shape before spending a single real API call.
    First run Simulates every probe and produces the same reports the real run would.
  5. Fire the probes for real against the live assistant.
    npm run eval:probe -- --contract outputs/eval/contract-teacher-<hash>-probes.json
    Why The proof step: every probe prompt goes to the live assistant, every reply is checked, and negative tests where refusal is correct are judged by the inverted rule.
    First run Fires every probe one at a time, with a short pause between each to avoid rate limits.
    Re-run Safe to re-run any time — after a system-prompt edit or a model upgrade — each run writes its own timestamped scorecard.
  6. Open the compliance scorecard.
    open outputs/eval/probe-runs/probe-run-<model>-<timestamp>.md
# a short plain-text version anyone can paste into chat:
open outputs/eval/probe-runs/probe-run-<model>-<timestamp>-SUMMARY.txt
    Why The Markdown report has every probe, its prompt, the assistant's actual reply, and the pass/fail reason. The SUMMARY.txt is the short form — pass rate, latencies, and per-clause-type compliance — built to paste into a ticket.

What you give it

--contract <path>
The -probes.json file produced by The Rulebook Extractor.
--dry-run
Rehearses the run on simulated replies — no live calls, no cost.
--model <name>
Which model to test against (defaults to the one set in the environment).
environment variables
Which assistant to call and the token that authorizes it.

What comes back

probe-run-<model>-<timestamp>.json / .md
Every probe's prompt, reply, pass/fail result, and latency, plus the overall pass rate.
probe-run-<model>-<timestamp>-SUMMARY.txt
A short plain-text scorecard — pass rate and per-clause-type compliance — for pasting anywhere.
Running it again. Every run is independent — no state carries between them. Re-run as often as you like (after a system-prompt edit, after a model change, or on a schedule); each run gets its own timestamped scorecard to diff against the last.
Plug it into your stack. This is the proof-of-compliance step: the scorecard is what a team points to when they claim the assistant keeps its safety and behavior contract. Chain it straight after The Rulebook Extractor in CI so any system-prompt edit auto-re-tests the live assistant before the change ships.

1 / 6

Loads the probe suite

When it runs
First, before any call to the assistant.
Takes in
The -probes.json produced by The Rulebook Extractor.
Shows out
A probe list, each bound to the clause it verifies and the prompt it sends.
2 / 6

Fires each probe at the live assistant

When it runs
Once per probe, in order.
Takes in
One probe prompt.
Shows out
The assistant's real reply and the latency of both the conversation setup and the reply.
3 / 6

Runs deterministic checks on the reply

When it runs
Right after each reply returns.
Takes in
The reply text and the check type (contains, not_contains, matches_regex, ...).
Shows out
A pass/fail per check, with a plain-English reason.
4 / 6

Applies the negative-test override

When it runs
When deciding the overall verdict.
Takes in
Whether the content filter blocked the request, and whether this is a negative test (refusal is correct).
Shows out
A PASS when the assistant correctly refuses or is blocked — instead of treating the block as an error.
5 / 6

Optional LLM-judge second opinion

When it runs
Only when quality checking is enabled for the run.
Takes in
The prompt, the reply, and the expected behavior.
Shows out
An extra pass/fail on tone and helpfulness, folded into the verdict.
6 / 6

Aggregates the scorecard

When it runs
Last, once every probe has run.
Takes in
Every probe's verdict and latency.
Shows out
An overall pass rate, latency percentiles, and per-clause-type compliance — reproducible via --dry-run without live calls.
