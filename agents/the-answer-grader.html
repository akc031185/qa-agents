Grading the AI assistant's answers

The Answer Grader

Turns a spreadsheet of test prompts into a golden dataset, runs each against the live assistant, and grades every answer PASS / WARNING / FAIL.

Source file: user-prompt-eval-agent.ts

A team's expected-behavior prompts usually live in a spreadsheet. This agent normalizes that sheet into a versioned golden dataset, sends each prompt to the live assistant, scores every response against a fixed rubric plus privacy/safety gates, and returns a report card with a pass rate, an overall verdict, and a per-prompt breakdown.

Why this exists

The chore it removes

Grading by hand means a tester copies each prompt out of the sheet, pastes it into the assistant, reads the reply, and decides per prompt whether it passes — while also watching for leaked PII or off-topic drift. At hundreds of prompts it's exhausting, inconsistent, and impossible to reproduce identically.

→
What you get instead

Every prompt is issued automatically, every response scored on the same rubric, and you get one report with a pass rate, an overall verdict, and a per-prompt breakdown — reproducibly, every run.

This is the report card that says whether the assistant is production-ready or still failing too many answers.

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node >= 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • A spreadsheet of test prompts — a prompt column plus, ideally, expected-output, keywords, and difficulty columns (any header names; the agent auto-maps them).
  • The assistant API's base URL and access token, so the agent can issue the prompts live.
  • The toolkit's local checker service running, so each response is scanned for PII and scored for quality.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program executed by Node. One-time install per machine.
    First run Needed only the first time on a new machine.
  2. Clone the agent code, install dependencies, and start the local checker service.
    cd path/to/the-agents
npm install

# one-time: install the checker service's own dependencies
npm run eval:service:install

# then start it (leave this running in its own terminal tab)
npm run eval:service:start
    Why npm install pulls the xlsx reader and the assistant client. The checker service is a separate process that runs the PII/safety scan and quality score — it must be up before grading.
    First run Installs everything and starts the service listening locally.
    Re-run Leave the service up across grading runs — no restart per run.
  3. Point it at the assistant (env vars).
    export APP_API_URL=https://your-assistant-host.example.com
export APP_API_TOKEN=your-access-token
export APP_MODEL=gpt4o
    Why Read at startup: which assistant to query and the token that authorizes it. Nothing is hard-coded — swap these to retarget environments.
  4. Convert the spreadsheet into a golden dataset.
    npm run eval:user:convert -- --input path/to/questions.xlsx
    Why Parses the raw sheet, resolves the column mapping, and writes a versioned golden dataset JSON. Omitting --input generates a small sample sheet first, so there's always something to run.
    First run Reads every row and builds the dataset from scratch.
    Re-run Idempotent — re-run whenever the sheet changes; each run writes a fresh, separately named dataset.
  5. Grade a --limit 10 batch first, then the full dataset.
    # quick spot-check — first 10 questions
npm run eval:user:run -- --limit 10

# the full run
npm run eval:user:run
    Why The limited run confirms the assistant is reachable and the checker service is scoring before you issue every prompt. Dropping --limit grades the whole dataset.
    First run Issues every prompt live, grades each response, and tallies the pass rate.
    Re-run Each run is an independent pass with its own timestamped report — no state carries over.
  6. Open the report card.
    open outputs/eval/eval-run-<timestamp>.md
# a plain-text version anyone can paste into chat:
open outputs/eval/eval-run-<timestamp>-SHAREABLE.txt
    Why The Markdown report has the full per-prompt breakdown, gates, and scores. The -SHAREABLE.txt is a short summary built to paste straight into a chat message or ticket.

What you give it

--input <path>
The spreadsheet of test prompts to convert into a golden dataset.
--dataset <path>
Which dataset to grade; without it, the agent auto-selects the most recently converted one.
--limit <n>
Grade only the first N prompts — a spot-check.
environment variables
Which assistant to call and the token that authorizes it.

What comes back

golden-<id>.json / .md
The versioned golden dataset and its human-readable summary.
eval-run-<timestamp>.json / .md
The full grading run — every prompt, its response, its scores, and its PASS / WARNING / FAIL verdict.
eval-run-<timestamp>-SHAREABLE.txt
A short plain-text summary — pass rate and overall verdict — for pasting anywhere.
Running it again. Convert is idempotent — re-run on any source-sheet change and it writes a fresh dataset. Grading is stateless too: each pass is a full, independent grade of the whole dataset, so re-run after any change to the assistant for a current report card.
Plug it into your stack. This is the report card a team hands up to gate a release. Wire the full run into CI on a schedule (or pre-release) so the pass rate stays current, and treat any drop as a release blocker.

Parses the spreadsheet

A spreadsheet in whatever column layout the team already uses.

Queries the live assistant

When it runs
Once per prompt in the dataset.
Takes in
One prompt at a time.
Shows out
The assistant's real response, captured via its chat client — no copy-paste.

Runs the PII and safety gates

When it runs
Immediately after each response returns.
Takes in
The prompt and the response.
Shows out
A pass/fail on whether the response leaked PII or produced unsafe content.
4 / 6

Scores quality with an LLM judge

When it runs
Alongside the gates.
Takes in
The prompt and the response.
Shows out
A multi-dimension quality rating, plus a keyword-match check confirming expected key terms appeared.
5 / 6

Combines into a verdict

When it runs
Once both checks return for a response.
Takes in
The gate results and the quality scores.
Shows out
One aggregate score and a PASS / WARNING / FAIL verdict — a failed PII gate hard-fails.
6 / 6

Emits the report

When it runs
Last, after every prompt is graded.
Takes in
Every graded response.
Shows out
A JSON data file, a detailed Markdown report, and a short shareable text summary.
