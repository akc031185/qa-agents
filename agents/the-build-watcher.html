Keeping the project tracker up to date

The Build Watcher

Triggers an ADO pipeline run and polls it to completion, returning a pass/fail verdict — no tab-refreshing to catch the result.

Source file: ado-pipeline-agent.ts

Fire-and-forget CI/CD. This agent POSTs a pipeline run to the ADO REST API, polls its state on a fixed interval, and reports succeeded/failed the moment the run terminates. Build, test, or deploy pipelines — same flow.

Why this exists

The chore it removes

Kick off a pipeline, then keep flipping to a browser tab every few minutes to check if it's done. A run can take 30 minutes. Focus drifts, failures go unnoticed for an hour, and cancelling a hung run means hunting through the ADO UI for the stop button.

→
What you get instead

The agent triggers the run, then polls getRunStatus every 30s until state === 'completed', then prints the result, elapsed time, and run URL. On request it fetches published artifacts or PATCHes a stuck run to canceling — all headless.

A failed build caught in seconds instead of an hour keeps the team from stacking work on a broken base.

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Azure DevOps access and a PAT with pipeline read/execute scope.
  • The pipeline IDs you want to run — build, test, and/or deploy — from whoever owns your CI setup.

Step by step

  1. Install Node.js — the engine that runs the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript run under Node — a one-time per-machine install.
    First run One-time setup per machine.
  2. Clone the agent and install its dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the agent's dependencies into node_modules.
    First run Cold install — a minute or two.
    Re-run No-op unless package.json changed.
  3. Set the target org, project, PAT, and pipeline IDs (env vars).
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
export ADO_BUILD_PIPELINE_ID=123
export ADO_TEST_PIPELINE_ID=124
export ADO_DEPLOY_PIPELINE_ID=125
    Why Read at startup: which ADO org/project to hit, the PAT that authorizes it, and which pipeline ID maps to build/test/deploy. Nothing is hard-coded — swap these to point at another project.
  4. Trigger a run and poll it.
    npm run ado:pipeline -- trigger 123 --branch main
# note the run number it prints, e.g. "Run #4821", then:
npm run ado:pipeline -- wait 123 4821
    Why trigger starts the run and returns its ID; wait polls that run every 30s until it reports succeeded or failed.
    First run Triggers a fresh run and polls it end to end.
    Re-run Each trigger starts a new run with its own ID — never reused.
  5. Read the printed verdict.
    # no file to open — the result prints straight to the terminal, e.g.:
# { "success": true, "data": { "runId": 4821, "result": "succeeded", "url": "..." } }
    Why No report file is written — the output is the immediate succeeded/failed verdict plus the run URL, printed straight to stdout.

What you give it

trigger <pipeline-id> [--branch <name>]
Triggers a run of the pipeline on the given branch (defaults to main).
wait <pipeline-id> <run-id>
Polls a run every 30s until completed, then reports succeeded/failed.
cancel <pipeline-id> <run-id>
PATCHes a stuck run to canceling.
environment variables
Target ADO org/project, the PAT, and the pipeline IDs for build/test/deploy.

What comes back

console verdict
Succeeded or failed, run duration, and the run URL — printed to stdout, not persisted.
artifact list (on request)
Names, sizes, and signed download URLs of the artifacts a successful run published.
Running it again. No stored state — every trigger is a fresh run with its own ID. Re-running on the same branch just starts the pipeline over, which is exactly what you want after pushing a fix.
Plug it into your stack. Wire the trigger + wait pair into whatever kicks off your CI/CD flow (a pre-merge gate, a nightly build) so no one refreshes a status page — the agent reports back the moment there's a verdict.
