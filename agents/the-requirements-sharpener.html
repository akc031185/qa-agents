Deciding what to test

The Requirements Sharpener

Rewrites a vague requirement into precise, testable Given/When/Then criteria grounded in the actual design screenshots — additively, never overwriting the original.

Source file: story-ac-refinement-agent.ts

Requirements are usually written before the design exists, so they stay fuzzy — 'the user can submit the form' with no real button labels or error messages. This agent feeds the requirement plus the finished design screenshots to a multimodal LLM and gets back sharp criteria that quote the actual on-screen text and cite the screen each came from. The original acceptance criteria are read once and never written back — the sharpened set is stored alongside.

Why this exists

The chore it removes

Making a requirement like 'show an error if the input is invalid' testable means cross-referencing it against the design mockups by hand: the exact error wording, the precise button label, which states are disabled, what the empty screen reads — then rewriting each point. It's meticulous, and anything missed becomes a gap a tester hits later.

→
What you get instead

The agent pulls the requirement, the prior feature briefing, and the exported design package — including the screenshots as base64 image data — and sends them to a multimodal Gemini model that reads the pixels, not just descriptions. It returns Given/When/Then criteria that quote exact labels and messages and cite the source screen, added alongside the untouched original.

Vague requirements produce vague tests that miss real defects. Grounding every criterion in the actual design closes that gap before the first test is authored.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Read access to Azure DevOps and a personal access token (ADO_PAT).
  • A Google Gemini API key — this agent needs a multimodal model, since it sends the design screenshots directly.
  • A folder of exported design files (frame-structure JSON, a text listing, and the screenshots).
  • Ideally a prior feature briefing from the Test Scout — the agent runs without one under --allow-no-intelligence.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program executed under Node. One-time install per machine.
    First run First time on a new machine only.
  2. Clone the code and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install resolves the agent's dependencies — the ADO REST client, the xlsx/docx writers, and the Gemini client — into node_modules.
    First run Downloads everything (a minute or two).
    Re-run No-op unless the dependency set changed.
  3. Set the environment variables.
    export ADO_PAT=your-access-token
export GOOGLE_API_KEY=your-gemini-key
    Why Read at startup — the PAT to fetch the story, the Gemini key for the multimodal call that reads the requirement and the design screenshots together and writes sharper criteria.
  4. Point it at the requirement and its design folder — dry-run first.
    npx ts-node agents/story-ac-refinement-agent.ts \
  --story-ids 6001 \
  --figma-dir ./designs/feedback-screen \
  --dry-run
    Why --story-ids is the requirement ticket number(s); --figma-dir is the exported design folder. --dry-run fetches everything and confirms the story and designs resolved, without an LLM call.
    First run Fetches the story, checks for a prior briefing and usable design files, and skips the LLM step.
  5. Run for real.
    npx ts-node agents/story-ac-refinement-agent.ts \
  --story-ids 6001 \
  --figma-dir ./designs/feedback-screen \
  --word
    Why Drop --dry-run. Sends the requirement, the prior briefing (if found), and the screenshots to the multimodal model and gets back sharper Given/When/Then criteria. --word also writes a docx.
    First run Generates the sharpened criteria and writes every output.
    Re-run No change-tracking — recomputes fresh from the current requirement text and designs; re-run whenever the design updates.
  6. If there's no prior briefing, allow the agent to proceed without one.
    npx ts-node agents/story-ac-refinement-agent.ts \
  --story-ids 6001 \
  --figma-dir ./designs/feedback-screen \
  --allow-no-intelligence
    Why By default the agent requires a prior feature briefing (from the Test Scout) for its business rules. This flag proceeds on the requirement text and designs alone.
  7. Open the sharpened criteria.
    open ./outputs/reports/story-ac-refinement/
    Why Outputs land as JSON, Markdown, an import-ready xlsx (one row per criterion), and — with --word — a docx. The original requirement wording is always preserved alongside, never overwritten.

What you give it

--story-ids <ids>
Comma-separated requirement ticket number(s) to sharpen.
--figma-dir <path>
A folder of exported design files — frame-structure JSON, on-screen text listing, and screenshots.
--word / --dry-run / --no-images / --allow-no-intelligence
--word adds a docx; --dry-run skips the LLM call; --no-images sends text only (no screenshots); --allow-no-intelligence proceeds without a prior briefing.

What comes back

StoryAC_Refinement_<timestamp>.json / .md
Every requirement's original criteria alongside the sharpened Given/When/Then criteria, each citing the source screen and label.
StoryAC_Refinement_<timestamp>.xlsx
One row per sharpened criterion — Story ID, Given, When, Then, Design Refs — ready to paste back into ADO.
StoryAC_Refinement_<timestamp>.docx
A shareable Word document (only with --word).
Running it again. No change-tracking — every run re-reads the requirement and design folder fresh. Re-run whenever the design changes (a new screenshot, an updated label) or the requirement's wording is edited; the original text is never overwritten, so nothing is lost by re-running.
Plug it into your stack. Feed it the briefing from the Test Scout for richer, rule-aware criteria. Its sharpened output is the ideal input to the Test-Plan Author — precise Given/When/Then criteria yield far more accurate drafted test cases than a vague one-line requirement.
