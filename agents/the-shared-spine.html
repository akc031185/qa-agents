The Shared Spine

The config seam every agent shares: reads env vars once, computes a capability map, and degrades each agent to offline instead of crashing.

Source file: src/core/config.ts

The backbone all agents share. loadConfig() reads the env once, treats blanks and placeholders as unset, and computes a capabilities map — ado, api, db, llm — from what's genuinely present. Agents gate optional behaviour on that map and call requireCapability() only where they truly can't proceed, so a missing credential yields a clear message or an offline fallback, never a crash. It's why the whole kit runs with or without Azure, on whatever subset a team has.

Why this exists

The chore it removes

The prior setup copy-pasted the same env — org, project, board URL, PATs — into dozens of scripts, each assuming everything was present and connected. A missing piece failed with a confusing error deep in a later call, and there was no single way to ask 'what can I actually run right now?'

→
What you get instead

One loadConfig() reads every setting and returns a capability map plus per-capability issues hints — always a usable config, degraded or not. Agents branch on cfg.capabilities.*; requireCapability() throws one actionable error at the exact point an ability is needed. npm run doctor prints the whole scorecard, secrets redacted. The kit runs on any subset — cloud or none.

The same toolkit runs for a team on full Azure and for a team with almost nothing configured — no rewrites, no dead ends. Every agent asks the config what it can do before it tries, so the result is simply the subset that can run, running.

See it in action

Run it & wire it in

You can run this yourself, end to end — every command below is real.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Node.js (installed in step 1 below) — nothing else.
  • No credentials, board, database, or API key are needed for the demo below — that is the point of this module. A .env only matters later, if you point it at something real.

Step by step

  1. Install Node.js — the runtime.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The toolkit is TypeScript on Node. One install per machine; no other runtime required.
    First run First time on a new machine only.
  2. Clone and install dependencies.
    cd path/to/qa-agent-toolkit
npm install
    Why npm install pulls the toolkit's only dependency (dotenv) into node_modules. No DB driver, no cloud SDK, no auth library — which is why the demos run credential-free.
    First run Downloads everything (seconds — the dependency list is tiny).
    Re-run No-op unless the dependency list changed.
  3. (Optional) copy the env template — only to go live later.
    cp .env.example .env
# then open .env and fill in ONLY the section you need
    Why Skippable for the demo — every capability is off by default and the demo runs regardless. .env matters only once you point the toolkit at a real board, service, or database.
  4. Run the capability check.
    npm run doctor
    Why Prints a one-line scorecard per capability (tracker, API, database, AI) — on/off with a reason. With an empty .env everything reads (off), which is expected: nothing here needs to be on.
  5. Run the health check — this IS the demo for this plate.
    npm run doctor
    Why doctor.ts calls the real loadConfig() and prints its capability scorecard — with nothing in .env, every capability legitimately reads (off), which is exactly the point: the spine doesn't crash or complain, it tells you plainly what won't run and why.
    First run With no .env (or a blank one), every capability shows ⚪ (off) with a one-line hint on the setting that would turn it on.
    Re-run Run it again after adding one line to .env (e.g. API_BASE_URL=https://jsonplaceholder.typicode.com) and exactly that capability flips to ✅ — nothing else changes.
  6. Flip one capability on and rerun, to see the spine react.
    cp .env.example .env
echo 'API_BASE_URL=https://jsonplaceholder.typicode.com' >> .env
npm run doctor
    Why The whole design in one before/after: add one setting and only the 'API testing' line flips from ⚪ (off) to ✅ target · https://jsonplaceholder.typicode.com — tracker, database, and AI stay exactly as they were, degraded or not.

What you give it

nothing
loadConfig() reads whatever is in .env (or the real environment) and never throws on missing values — run it with no .env at all and it still returns a complete, usable config with every capability off.
any subset of the env vars
ADO_ORG/ADO_PROJECT/ADO_PAT, API_BASE_URL/API_BEARER_TOKEN, DB_CONNECTION_STRING/DB_BRIDGE_DIR, GOOGLE_API_KEY/ANTHROPIC_API_KEY — fill in only the ones you have; each is independently optional.

What comes back

console scorecard
One line per capability (ADO, API, DB, LLM) — a ✅/⚪ mark, on/off, and either where it's pointed (live) or exactly which setting would turn it on (off). Never prints a secret value.
offline-mode note
If ADO_ORG/ADO_PROJECT are set but ADO_PAT is not, an extra line explains the tracker is in OFFLINE (fixture) mode rather than failing.
Running it again. Safe and cheap to run any time, on any machine, in any state — it only reads env vars and mutates nothing. Add or remove a setting in .env and the next npm run doctor reflects it immediately.
Plug it into your stack. Import the seam directly: import { loadConfig, requireCapability } from './src/core/config'; call loadConfig() once at startup, gate optional behaviour behind cfg.capabilities.ado / .api / .db / .llm, and call requireCapability(cfg, 'db') at the one point an agent truly can't proceed without it — you get a clear, actionable error instead of a cryptic failure three calls deep. Every other plate in this toolkit (tracker, report, API, DB) is built on exactly this pattern.
