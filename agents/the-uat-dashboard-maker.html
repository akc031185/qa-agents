Turning results into reports people read

The UAT Dashboard Maker

Parses the returned UAT spreadsheet — even a wide-format sheet several testers filled side by side — and emits a one-slide dashboard, an HTML page, and raw JSON with the go/no-go call computed.

Source file: uat-dashboard-agent.ts

The last gate before launch is UAT: real users exercise the app and log pass/fail plus comments into an .xlsx workbook. This agent parses that workbook — detecting when multiple testers shared one sheet in wide format — aggregates pass/fail counts, classifies failures into buckets, computes coverage and pass rate, evaluates them against exit criteria, and renders a single PowerPoint slide plus a self-contained HTML dashboard showing coverage, pass rate, the issue list, and launch readiness.

Why this exists

The chore it removes

The manual path: open the returned workbook, count prompts tried, passed, and failed, bucket the failures, compute the pass rate, check it against exit criteria, then hand-build a summary slide for the go/no-go meeting. Error-prone counting plus hours of slide work, redone every time a fresh workbook comes back.

→
What you get instead

Point the agent at the workbook (or the folder it lands in) and get back a finished dashboard slide, a matching HTML page, and the raw JSON — counting, classification, and exit-criteria evaluation all done.

The go/no-go launch decision rests on these numbers, so counting them correctly and rendering them unambiguously is exactly what a room of decision-makers needs.

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • The filled-in UAT workbook (the final round where real users exercise the app before launch) as an .xlsx file, or a directory where those get dropped.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program; Node executes it. One-time per machine.
    First run Needed only the first time on a new machine.
  2. Clone the agents and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the agent's dependencies — xlsx for parsing and pptxgenjs for the slide — into node_modules.
    First run Downloads everything (a minute or two).
    Re-run No-op unless the dependency list changed.
  3. No env vars needed — just know where the workbook lives.
    # example: a single returned workbook
./returned-uat-results.xlsx

# or a shared folder several testers dropped their copies into
./uat-results/
    Why Unlike agents that hit a work board or an LLM, this one only reads a local .xlsx — there's nothing else to configure.
  4. Dry-run first, writing no files.
    npm run uat:dashboard -- --input ./returned-uat-results.xlsx --dry-run
    Why --dry-run prints the aggregated numbers — coverage, pass rate, issues, exit criteria — to stdout, so you can verify the sheet parsed correctly before rendering the slide.
  5. Run for real and open the dashboard.
    npm run uat:dashboard -- --input ./returned-uat-results.xlsx

open outputs/reports/uat/UAT_Dashboard_<timestamp>.pptx
open outputs/reports/uat/UAT_Dashboard_<timestamp>.html
    Why Without --dry-run, it writes all three deliverables: a one-slide PowerPoint with ring and bar charts, a self-contained HTML page, and the raw JSON — ready to drop into the go/no-go meeting.
    First run Parses every row, detects the tester layout, and builds all three files fresh.
    Re-run Point --input at the folder instead of one file and it always picks the newest .xlsx by mtime — handy once a newer round of results comes back.

What you give it

--input <path>
A single .xlsx workbook, or a directory — in which case the newest .xlsx by mtime is used.
--dry-run
Print the aggregated summary to stdout only; skip writing the .pptx, .html, and .json.

What comes back

UAT_Dashboard_<timestamp>.pptx
A one-slide PowerPoint with coverage and pass-rate ring charts, issue bar charts, and the four exit-criteria checks.
UAT_Dashboard_<timestamp>.html
A self-contained HTML dashboard of the same metrics, shareable without opening PowerPoint.
UAT_Dashboard_<timestamp>.json
Every aggregated number in raw form — coverage, pass rate, issues by bucket, and the exit-criteria checklist.
Running it again. Re-run whenever a fresh workbook comes back from a new tester round — point --input at the shared drop folder and it always picks the newest file by mtime, so the dashboard never goes stale. Nothing needs clearing between runs; each writes a new timestamped set of files.
Plug it into your stack. Drop the completed workbook into the shared folder as the last step of a UAT round, then run this agent as the trigger for the go/no-go meeting — the .pptx is what gets projected, the .json is what gets archived alongside the decision.

Under the hood — for the curious

A slide for each moving part. Slide back and forth.

1 / 6

Resolve the workbook

When it runs
First, on the input path you pass.
Takes in
A file path, or a directory where testers drop filled-in workbooks.
Shows out
One resolved .xlsx path — the newest by mtime when a directory is given (via resolveInputFile()).
2 / 6

Parse the workbook

When it runs
Immediately after the file is resolved.
Takes in
The 'Sample Prompts', 'New Prompts', and 'Testers' sheets in the workbook.
Shows out
Every row parsed into structured records via the xlsx library.
3 / 6

Detect tester layout

When it runs
As each sheet is parsed.
Takes in
The header row and the row below it.
Shows out
Either a single-tester layout, or — via repeating Tester #N column blocks every six columns — a multi-tester layout with each tester's columns mapped correctly (via detectWideFormat()).
4 / 6

Aggregate metrics

When it runs
After every row from every sheet is parsed.
Takes in
The full list of per-test results — pass, fail, or untested — across all testers.
Shows out
Coverage, pass/fail counts, and pass rate for the Sample and New prompt sheets, combined into one set of totals (via aggregateMetrics()).
5 / 6

Classify failures and evaluate exit criteria

When it runs
Once the totals are known.
Takes in
Every failed result and its comment.
Shows out
Issue counts per named bucket, plus a met/not-met/pending evaluation of the four exit criteria: coverage, pass rate ≥ 80%, zero high-severity issues, and formal sign-off (via classifyIssues()).
6 / 6

Render the deliverables

When it runs
Last, unless --dry-run was passed.
Takes in
The finished metrics object.
Shows out
A one-slide PowerPoint (ring and bar charts via pptxgenjs), a matching self-contained HTML dashboard, and a JSON dump of every number, ready for the go/no-go meeting (via generatePptx()).
