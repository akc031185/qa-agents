The Release-Readiness Inspector

Replays every fixed bug's repro in a headless-capable Playwright browser, P1-first, and returns a pass-rate go/no-go verdict.

Source file: bug-release-testing-agent.ts

Pulls the Closed/Resolved bugs under the features being released, runs a deterministic testability analysis to decide which can be automated, then drives a real Chromium session through each repro against your environment. Returns a release-readiness report — overall pass rate and a separate P1 pass rate — plus a screenshot per bug, most-critical first.

Why this exists

The chore it removes

Every release, a tester is supposed to re-open each fixed bug, read the repro, and manually click through to confirm it holds and nothing adjacent regressed. Across dozens of bugs under time pressure it gets rushed, and the urgent ones don't reliably get checked first.

→
What you get instead

An automated re-check in a real browser, priority-ordered (P1 before P2/P3/P4), with a PASS/FAIL and screenshot per bug — plus an explicit SKIP list of what a browser genuinely cannot verify and why.

A fix that quietly regressed erodes trust fast. This catches those regressions pre-ship, and the P1 pass rate is a hard go/no-go number a pipeline can gate on.

What this step does

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • An Azure DevOps org/project and a PAT with work-item read scope.
  • A reachable running instance of the app under test (a dev/QA URL) and a way past its sign-in (SSO creds, or manual login on first run).
  • Playwright's Chromium binary installed — a real browser is driven per check, so this is mandatory.
  • No LLM key — testability decisions are deterministic keyword rules, kept fully local (no bug text leaves the machine).

Step by step

  1. Install Node.js — the runtime.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript on Node. One-time per machine.
    First run First time only, on a new machine.
  2. Install dependencies and the Chromium binary.
    cd path/to/the-agents
npm install
npx playwright install chromium
    Why npm install pulls the ADO client and report writers; playwright install fetches the actual browser binary the agent drives. Skip it and the run fails immediately.
    First run Dependencies plus a ~300MB browser binary — a few minutes.
    Re-run No-op once installed, unless the browser version changed.
  3. Export the ADO target and (optionally) sign-in (environment variables).
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
export APP_SSO_PASSWORD=your-password   # optional — omit to log in by hand on first run
    Why Read at startup to resolve the board and, if the app's SSO page appears, get past it headlessly without a human at the keyboard.
  4. Dry-run the testability analysis — no browser yet.
    npm run bug:release:dry -- --feature-ids "4001,4002"
    Why --dry-run fetches the closed bugs and runs testability analysis only — reports the automatable-vs-skip split before spending time driving Chromium.
  5. Run the real re-check against your environment.
    npm run bug:release -- \
  --feature-ids "4001,4002" \
  --app-url https://qa.my-app.example.com \
  --limit 20

# or headless + a Word report in one go:
npm run bug:release:headless -- --app-url https://qa.my-app.example.com --word
    Why The actual re-check: drives Chromium, signs in, replays each bug's action sequence P1-first, capped at --limit.
    First run May block on a manual SSO login if no password/session was configured.
    Re-run Faster once a saved session exists — later runs skip the login round-trip.
  6. Open the release-readiness report.
    open ./outputs/reports/bug-release/BugRelease_<timestamp>.md
open ./outputs/reports/bug-release/screenshots/
    Why The .md surfaces the overall and P1 pass rates; the screenshots folder holds one image per bug to eyeball anything FAIL or SKIP.

What you give it

--feature-ids <ids>
Comma-separated feature IDs to pull Closed/Resolved bugs from.
--query-url <url>
A saved tracker query URL to source bugs from instead of walking features.
--app-url <url>
Target environment to drive directly (overrides --env).
--env <dev|qa>
Named environment to target, if --app-url isn't given.
--headless
Run Chromium with no visible window (for CI).
--dry-run
Testability analysis only — skip driving the browser.
--limit <n>
Cap on automatable bugs actually run, P1 first (default 20).
--word
Also serialize a .docx report.
environment variables
Org/project target, the PAT, and (optionally) an SSO password.

What comes back

BugRelease_<timestamp>.json
Full structured report — PASS/FAIL/SKIP per bug, overall pass rate, P1 pass rate.
BugRelease_<timestamp>.md
The same report rendered for a go/no-go read.
BugRelease_<timestamp>.docx
Shareable Word version, only with --word.
screenshots/
One final-state screenshot per checked bug, PASS or FAIL.
Running it again. No result caching — bug data and browser session are always fresh — but a saved sign-in session (once established) skips the manual-login wait on later runs. Re-run right before each release to catch anything that regressed since the last check.
Plug it into your stack. Wire it as a release gate in CI — headless, against QA, after deploy and before promote-to-prod. Fail the pipeline when the pass rate (or specifically the P1 pass rate) drops below threshold, and archive the screenshots folder as release evidence.

The action sequence + target environment.

A real Playwright session — locate/fill/press/wait against live selectors, capturing the app's actual responses.

Every PASS / FAIL / SKIP result.
