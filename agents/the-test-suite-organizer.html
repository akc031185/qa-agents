The Test-Suite Organizer

Bulk-organizes an ADO test suite — files test cases into suites, repairs broken TestedBy links, normalizes titles to a naming convention, and reassigns testers.

Source file: ado-suite-manager-agent.ts

A team keeps hundreds of test cases organized in suites under an ADO Test Plan. This agent maintains that structure at scale: it adds test cases to suites, audits each for a missing or reversed TestedBy link to its parent story, normalizes titles to the TC_US<storyId>_ convention, and drives tester ownership across the work item, the test case, and its test point.

Why this exists

The chore it removes

By hand, keeping a suite tidy is soul-crushing. Someone opens suite after suite, checks each test case's title against the convention, confirms it's linked to the right story in the right direction, and records its owner — across hundreds of items. Titles drift, links point the wrong way, and reassigning work when someone leaves means editing dozens of items one at a time.

→
What you get instead

The agent does the whole sweep in one pass. It lists suite contents, adds test cases, and — most usefully — audits every case for three defects: a missing TestedBy-Reverse link, a reversed (TestedBy-Forward) link, and a title that breaks the naming convention. It reports each, and on approval fixes them. It also reads a feature's stories to auto-assign each test case to its author, and bulk-reassigns ownership when it changes.

When every test case is filed, named, and owned correctly, a lead can trust the Test Plan at a glance instead of second-guessing whether anything is where it claims to be.

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Azure DevOps Test Plans access and a PAT scoped to edit work items and test points.
  • The Test Plan ID and suite ID you want to organize — both visible in the ADO URL when you open the suite.

Step by step

  1. Install Node.js — the engine that runs the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript run under Node — a one-time per-machine install.
    First run One-time setup per machine.
  2. Clone the agent and install its dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the ADO client and xlsx reader into node_modules.
    First run Cold install — a minute or two.
    Re-run No-op unless package.json changed.
  3. Set the target org, project, and PAT (env vars).
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
    Why Read at startup: which ADO org/project to hit and the PAT that authorizes the writes.
  4. Audit first with --dry-run.
    npm run ado:suite:validate -- --plan-id 1201 --suite-id 1202 --dry-run
    Why --dry-run prints every test case with a missing link, reversed link, or off-convention title, but writes nothing. Review the list before letting it write.
    First run Reads every test case in the suite and reports defects.
  5. Approve by re-running without --dry-run.
    npm run ado:suite:validate -- --plan-id 1201 --suite-id 1202
    Why Same audit, but now it repairs the TestedBy links and normalizes the titles it flagged.
    Re-run Idempotent — anything already correct is skipped; only remaining defects get fixed.

What you give it

--plan-id <id> --suite-id <id>
Which Test Plan and suite to operate on.
--validate-links [--dry-run]
Audits (and, without --dry-run, repairs) missing/reversed TestedBy links and off-convention titles.
--assign-testers / --reassign-map
Sets or bulk-reassigns test case ownership to a tester.
--input <xlsx>
A list of test case IDs to add to the suite.

What comes back

console audit report
Every defect found — missing link, reversed link, or off-convention title — with a before/after for each rename.
updated tracker items
Once approved: the test case's TestedBy link and/or title corrected directly in ADO; no local file is produced.
Running it again. Idempotent — every pass only reports (and, if approved, fixes) remaining defects; anything already correct is skipped, so the output shrinks as the backlog clears.
Plug it into your stack. Run the --dry-run audit as a weekly health-check job and forward the report only when it's non-empty — a clean suite yields an empty report, which is itself useful signal.
