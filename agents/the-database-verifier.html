The Database Verifier

One reconciliation engine that checks a displayed value against the record behind it — seven compare modes, pure and offline, no DB required.

Source file: src/core/db.ts

A single compare() engine that reconciles a source-of-truth value against a value-under-test across seven modes — exact, numeric tolerance, set, contains, presence, empty, count. It's a pure function with no I/O, so the comparison logic needs no database, network, or credentials. Optional jsonPath() extraction and a direct-or-bridge SQL backend feed it real data when you go live; the same compare() runs in both.

Why this exists

The chore it removes

The prior setup meant opening the source records by hand, reading the real value, then flipping to the app to eyeball a match. Slow, mind-numbing, and easy to miss a subtle mismatch — a trailing space, a differently-formatted date, a same-set list in a different order.

→
What you get instead

One compare() engine takes two values, a mode, and returns a typed pass/fail with a reason. It normalizes both sides first — trim, lower, date — so a cosmetic difference isn't a false fail. It runs as a pure function, no DB attached; when you need real records, a direct connection or a folder-relay bridge fetches them, but the comparison itself is I/O-free and trivially unit-testable.

Catching a silent mismatch between what users see and what is actually stored prevents the kind of quiet data error that erodes trust in a whole system — and because compare() is a pure function, that logic is unit-testable with zero infrastructure.

Run it & wire it in

You can run this yourself, end to end — every command below is real.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Node.js (installed in step 1 below) — nothing else.
  • No credentials, board, database, or API key are needed for the demo below — that is the point of this module. A .env only matters later, if you point it at something real.

Step by step

  1. Install Node.js — the runtime.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The toolkit is TypeScript on Node. One install per machine; no other runtime required.
    First run First time on a new machine only.
  2. Clone and install dependencies.
    cd path/to/qa-agent-toolkit
npm install
    Why npm install pulls the toolkit's only dependency (dotenv) into node_modules. No DB driver, no cloud SDK, no auth library — which is why the demos run credential-free.
    First run Downloads everything (seconds — the dependency list is tiny).
    Re-run No-op unless the dependency list changed.
  3. (Optional) copy the env template — only to go live later.
    cp .env.example .env
# then open .env and fill in ONLY the section you need
    Why Skippable for the demo — every capability is off by default and the demo runs on inline sample data regardless. .env matters only once you point the toolkit at a real board, service, or database.
  4. Run the capability check.
    npm run doctor
    Why Prints a one-line scorecard per capability (tracker, API, database, AI) — on/off with a reason. With an empty .env everything reads (off), which is expected: the demo needs none of them on.
  5. Run the DB-verification demo — reconcile a synthetic DB row against a synthetic API body.
    npm run demo:db
    Why Feeds the real recon engine an inline synthetic 'DB row' and 'API response' and runs one check per mode — exact, numeric-tolerance, set, contains, presence, null, count — split into an all-pass group and an all-fail group, proving every mode works both ways.
    First run Runs all 16 checks (9 passing, 7 failing on purpose) and prints a results table per group plus a summary.
    Re-run Fully deterministic — same inline data every time, so the same 9 pass / 7 fail. No DB, network, or state at all.
  6. Read the pass/fail tables.
    # printed straight to the terminal — no file written:
#   EXPECTED-TO-PASS  (9/9 PASS)
#   EXPECTED-TO-FAIL  (7/7 FAIL, as intended)
#   Summary: compare modes exercised: contains, count, exact, null, numeric, presence, set (all 7)
    Why Each row shows the mode, the check name, and the exact detail — e.g. '|7.35-7.34| = 0.00999... <= tol 0.05' — so you see precisely why a check passed or failed, not just that it did.

What you give it

nothing
The demo defines its own synthetic dbRow (source of truth) and apiBody (value under test) inline in examples/db/demo.ts — no DB connection or credentials to exercise the compare engine.
DB_CONNECTION_STRING / DB_BRIDGE_DIR (optional, for real use)
Set one in .env to fetch the real expected side via live SQL — direct connection or folder-relay bridge for a locked-down DB — instead of a value already in hand.

What comes back

console tables
An 'EXPECTED-TO-PASS' table (9 checks, all PASS) and an 'EXPECTED-TO-FAIL' table (7 checks, all FAIL as intended) — one row per check with its mode and plain-English detail.
jsonPath + parseCsv showcase
Prints how jsonPath() extracts from a nested JSON body (e.g. data.regions[*].name) and how parseCsv() turns a bridge CSV response into rows — offline, on inline sample text.
summary line
'DEMO OK — recon engine ran with zero infrastructure.'
Running it again. Idempotent: the compare engine is a pure function of the inline dbRow/apiBody, so reruns always print the identical 9 pass / 7 fail. Point real checks at a live DbVerifier.scalar(sql) result and an actual API body, and the same compare() / runDbVerification() calls reconcile your real data.
Plug it into your stack. Import the pure engine directly: import { compare, jsonPath, normalizeVal } from './src/core/db' — compare() takes { name, mode, expected, actual } and returns a ReconResult with no I/O, so it's trivially unit-testable. For a full check list, use runDbVerification() (./agents/db) with an array of DbCheckSpecs and an apiBody; each result converts to report evidence via reconStep(), rendering alongside API and tracker checks in the same dashboard.
