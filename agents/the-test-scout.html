Deciding what to test

The Test Scout

Collapses a feature's scattered artifacts — ADO work items, design docs, meeting transcripts — into one structured, testable briefing.

Source file: test-intelligence-agent.ts

Kills the per-story ramp-up where a tester reconstructs a feature from ADO, Figma, specs, and a meeting recording. One command aggregates all of it into a structured briefing — flows, business rules, edge cases, integration points, open questions, confidence score — so the whole team tests against one model instead of re-deriving it story by story.

Why this exists

The chore it removes

A tester picks up a story with a three-line description. The real detail is spread across a Figma deck, a spec doc, an hour of recording, and child work items. Reconstructing a testable model by hand is slow and brittle — one missed decision silently changes the expected behavior.

→
What you get instead

Point it at a story ID and a document folder. It walks the ADO work-item tree, extracts text (pdf-parse for PDFs, mammoth for Word, a VTT parser for transcripts), sends transcripts to Gemini Flash for demonstrated behavior and decisions, then merges everything into a content-hashed JSON briefing: purpose, flows, business rules, edge cases, integration points, open questions, and a 0–100 confidence score. Re-runs are incremental — only changed sources are re-parsed.

A misunderstood feature produces the wrong test cases, and the defect ships however green they are. Shared understanding up front is the highest-leverage point in the QA cycle.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Read access to your Azure DevOps project and a personal access token (Work Items: Read).
  • A folder for the feature with its documents — design PDFs, spec .docx files, and any meeting-transcript (.vtt/.docx) files.
  • A Gemini API key for the transcript-summarization step; without it the agent still runs, rule-based only.

Step by step

  1. Install Node.js — the engine that runs the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a small TypeScript program; Node is the runtime that executes it. This is the one thing you install once per machine.
    First run Needed only the first time on a new computer.
  2. Get the agent's code and install the libraries it depends on.
    cd path/to/the-agents
npm install
    Why npm install downloads the helper libraries the agent uses — the work-board client, the PDF reader, the Word reader, and the AI client — into a local node_modules folder.
    First run Downloads everything (a minute or two).
    Re-run Skips straight past — already installed, unless the library list changed.
  3. Tell it which systems to talk to (environment variables).
    export ADO_ORG=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
export GOOGLE_API_KEY=your-gemini-key   # optional
    Why The agent reads these at startup to know which work board to open, which token proves it's allowed, and which AI to use. Nothing is hard-coded — swap these and it points at a different project.
  4. Point it at one feature and run it.
    npm run intelligence:folder -- \
  --story 4001 \
  --folder ./features/save-draft
    Why This is the actual run. npm run intelligence:folder launches the agent's built-in "read a feature folder" task — one of the named shortcuts defined in its package.json (think of it as pressing a labelled button that runs the real program underneath). The lone -- is npm's way of saying "everything after this belongs to the agent, not to npm", so the two options are passed straight through: --story is the feature's ticket number and --folder is where its documents live. Hitting Enter starts the whole read-and-summarize.
    First run Reads every source from scratch and builds the briefing.
    Re-run Only re-reads the documents that actually changed (it fingerprints each one), then writes a short changelog of what's different.
  5. Open the briefing it produced.
    open ./output/intelligence/story-4001.json
# and the readable summary:
open ./output/intelligence/story-4001.md
    Why The agent saves its work to disk. The .json is the structured briefing (for the next agent to consume); the .md is the same thing formatted for a human to read.

What you give it

--story <id>
The feature's ticket number on the work board.
--folder <path>
A folder holding the feature's design PDFs, spec Word docs, and meeting transcripts.
environment variables
Which board/project to read, the access token, and (optionally) the AI key.

What comes back

story-<id>.json
The structured briefing — purpose, user flows, rules, edge cases, open questions, and a confidence score.
story-<id>.md
The same briefing formatted for a person to read.
changelog (on re-run)
A short list of what changed since last time, so you don't re-read the whole thing.
Running it again. The second run is fast and quiet: the agent stored a fingerprint of every document it read, so it only re-summarizes the ones that actually changed and prints a changelog. Run it on a schedule and the briefing stays current on its own.
Plug it into your stack. The .json output is the hand-off to the next agent in the line — the Test-Plan Author — which turns the briefing straight into test cases. Drop this step into your CI pipeline so every new feature ticket automatically gets a briefing waiting for the tester.

Under the hood — for the curious

A slide for each moving part. Slide back and forth.

1 / 6

Reads the shared work board

When it runs
First, the moment the agent starts on a feature.
Takes in
A single story ID.
Shows out
The parent story plus its child tickets, filtered down to the ones about behaviour and screens (via the Azure DevOps REST API — the team's shared work-and-ticket board).
2 / 6

Parses the local documents

When it runs
Right after the tickets are pulled.
Takes in
The PDFs, Word docs, and meeting-transcript files sitting in the feature folder.
Shows out
Plain, searchable text — using pdf-parse for PDFs, mammoth for Word, and VTT/DOCX parsers for transcripts.
3 / 6

Summarizes transcripts with an AI model

When it runs
Once for each recorded meeting it finds.
Takes in
The transcript text and a short summary of the feature.
Shows out
A structured list of demonstrated features, decisions made, and open questions (produced by the Gemini Flash model).
4 / 6

Merges into one 'intelligence' file

When it runs
After every source has been read.
Takes in
All the extracted pieces together.
Shows out
A single structured JSON briefing, stamped with content hashes for change-tracking and a 0–100 confidence score.
5 / 6

Understanding first, test cases later

When it runs
Only if you explicitly ask for it.
Takes in
An opt-in flag.
Shows out
By default the agent stops at understanding; it will not write test cases unless told to — so it is safe to run just to learn a feature.
6 / 6

Its output can become an HTML page — via any LLM

When it runs
An optional step after the briefing is saved.
Takes in
The .json briefing (for the next agent to consume) or the human-readable .md.
Shows out
Because the briefing is plain, structured text, you can hand it to any LLM and ask for a polished HTML page, a slide, or a one-pager — no special integration needed. The sample beside this was generated straight from story-4001.json.
