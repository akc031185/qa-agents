Keeping the project tracker up to date

The Tracker Sync

Refreshes the master QA status workbook from live ADO data — hours, bug counts, statuses — via Microsoft Graph download/upload, no manual data entry.

Source file: qa-tracker-agent.ts

Teams keep a master status workbook — one row per feature/story, with columns for logged hours, bugs, pass/fail tallies, and status. This agent pulls the file from SharePoint over Microsoft Graph, queries ADO for the live figures, writes every cell with exceljs, and PUTs the updated workbook back.

Why this exists

The chore it removes

Keeping that workbook current is a weekly grind. Someone opens ADO, looks up each story's QA hours, counts its bugs, tallies pass/fail, checks status, and types it into the right cell — every row, every sprint. It takes hours, the numbers are stale the moment they're typed, and a fat-fingered figure quietly misleads everyone reading the report.

→
What you get instead

The agent downloads the workbook from SharePoint, then per story queries ADO for the real figures — logged QA hours (CompletedWork), child bug count, pass/fail, and System.State — and writes them into the current sprint's columns. It rebuilds a severity-color-coded bug sheet, refreshes each story's status, then uploads the file back. A --dry-run mode writes locally without publishing.

A status report that's automatically accurate means leadership decides on live numbers, not a workbook that quietly drifted out of date.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Azure DevOps access with a PAT, and SharePoint access with a Microsoft Graph token (needed only for the download/upload steps).
  • The master status workbook already on SharePoint, in the format this agent expects — a 'Sprint Tracker' sheet and a 'Feature Summary' sheet.

Step by step

  1. Install Node.js — the engine that runs the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript run under Node — a one-time per-machine install.
    First run One-time setup per machine.
  2. Clone the agent and install its dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls exceljs and the ADO/Graph clients into node_modules.
    First run Cold install — a minute or two.
    Re-run No-op unless package.json changed.
  3. Set the ADO and Graph credentials (env vars).
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
export GRAPH_API_TOKEN=your-graph-token   # only needed to download/upload
    Why The PAT reads live hours/bugs/status from ADO; the Graph token fetches and publishes the workbook. Without the Graph token it falls back to a local copy of the file.
  4. Preview a sync with --dry-run.
    npm run qa:tracker:sync -- --sprint S10
    Why --dry-run mode: downloads the current workbook, pulls the live figures from ADO, and writes a local copy — but skips the upload, so nothing on SharePoint changes yet.
    First run Pulls the full workbook plus every story's figures for the chosen sprint.
    Re-run Safe to repeat — it re-reads the latest figures each time.
  5. Run the real sync and publish it.
    npm run qa:tracker -- --sprint S10
    Why Same steps as the dry run, but PUTs the finished workbook back to SharePoint so the rest of the team sees the refreshed numbers.
    Re-run Idempotent — recomputes every cell from live ADO data and overwrites the previous version, so re-running (e.g. weekly) just keeps the sheet current.
  6. Open the local backup, if you just want to look.
    open outputs/reports/qa-tracker/Q3-2026/Q3_QA_Tracker.xlsx
    Why A local backup is always written before any upload, so you can inspect exactly what went out — or work fully offline with --local-only.

What you give it

--sprint <name>
Which sprint's columns to refresh (defaults to whichever sprint's dates cover today).
--dry-run
Sync from ADO but skip the SharePoint upload.
--local-only / --file <path>
Skip SharePoint entirely and read/write a local (or manually downloaded) copy.
--download-only
Just fetch the current workbook from SharePoint; don't sync or upload.

What comes back

Q3_QA_Tracker.xlsx (local backup)
Written before every run, with the sprint's hours/bugs and every story's status refreshed.
the same file, republished
PUT back to SharePoint so the whole team sees the current numbers (unless --dry-run or --local-only).
rebuilt Bug Summary sheet
Every bug under every story, sorted and color-coded by severity and state.
Running it again. Idempotent by design — every pass recomputes each cell from live ADO data and overwrites what was there, so running it weekly (or on a schedule) is exactly the intended use; no accumulating state goes stale.
Plug it into your stack. Schedule the real sync (not the dry run) to run at the start of each week so the status workbook leadership reads from is never more than a few days stale.

After the story rows are updated.

Every bug found under every story, across all features.

A sorted, severity-color-coded bug table on its own sheet.

Last, unless it's a dry run or local-only pass.

The updated workbook, written locally first.
Shows out
The file PUT back to SharePoint over Microsoft Graph, ready for the team to open.
