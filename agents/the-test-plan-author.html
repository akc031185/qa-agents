Deciding what to test

The Test-Plan Author

Drafts executable test cases from ADO user stories and, for stories too thin to test, emits a gap report naming the missing fields and their owners.

Source file: test-plan-generator.ts

Generates the test-case suite for a feature straight from its ADO work items — steps, expected results, priority — so testers stop hand-authoring checklists. In the same pass it detects stories that lack the detail to test (no description, no acceptance criteria, no design link) and produces a gap report with each blocker assigned to the person who owns the fix.

Why this exists

The chore it removes

Hand-authoring test cases per ticket — steps, test data, expected result — is slow and repetitive. Worse, a large fraction of tickets are untestable as written: no design references, no acceptance criteria. The tester either guesses at intent or blocks to chase the developer, one ticket at a time, and the questions trickle out over days.

→
What you get instead

The agent reads each story and drafts its test cases. For stories that aren't ready, it emits a gap report keyed by story: missing/short description, no acceptance criteria, no design reference — each tagged with the assignee — so the whole batch of questions goes back to the team in one round trip instead of one at a time.

Testers spend their time executing, not transcribing checklists. Blocked stories surface at draft time, before they stall execution late in the sprint.

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • Read access to Azure DevOps and a personal access token (ADO_PAT) with work-item read scope.
  • A Google Gemini API key to draft the actual test steps; without it the agent runs in no-LLM mode and produces the gap report only.
  • Optional: a folder of context documents — designs, prompts, screenshots — to ground the drafted cases.

Step by step

  1. Install Node.js — the runtime for the agent.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program executed under Node. One-time install per machine.
    First run First time on a new machine only.
  2. Clone the code and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install resolves the agent's dependencies — the ADO REST client, the xlsx writer, and the Gemini client — into node_modules.
    First run Downloads everything (a minute or two).
    Re-run No-op unless the dependency set changed.
  3. Set the environment variables.
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
export GOOGLE_API_KEY=your-gemini-key   # optional
    Why Read at startup: the ADO org/project to query, the PAT that authorizes it, and the Gemini key. Nothing is hard-coded — repoint these to target a different project.
  4. Draft test cases for a sprint.
    npx ts-node agents/test-plan-generator.ts \
  --sprint "Sprint-12" \
  --mode create
    Why The real run. --sprint scopes the iteration; --mode create drafts only for stories with no existing test cases — never duplicating linked work.
    First run Reads every story in the sprint, drafts cases for the testable ones, and emits a gap report for the rest.
    Re-run Idempotent — skips stories that already have test cases and touches only new or changed ones.
  5. Or run a coverage-and-gap report over a whole feature.
    npx ts-node agents/test-plan-generator.ts \
  --mode report \
  --feature-id 5001
    Why --mode report skips drafting and reports coverage percentage plus the exact tickets blocking the rest — a pre-release gate.
  6. Open the results.
    open ./outputs/reports/test-plans/
# or, for a report run:
open ./outputs/reports/feature-reports/
    Why Outputs land as Markdown, JSON, and Excel — Markdown for reading, Excel for testers, JSON for the next stage in the pipeline.

What you give it

--sprint <name> | --feature-id <id> | --stories <ids>
Scope selector — by sprint iteration, by feature, or by an explicit ID list.
--mode create|update|report|full
create = new stories only; update = re-draft where the content hash changed; report = coverage/gap only; full = both.
--context <folder>
Optional folder of design docs, prompts, and screenshots used to ground the drafted cases.
environment variables
ADO_ORGANIZATION, ADO_PROJECT, ADO_PAT, and optionally GOOGLE_API_KEY.

What comes back

test plan (Markdown / JSON / Excel)
Drafted test cases — steps, expected results, priority — per story, ready to push into ADO.
feature report (Markdown / JSON)
Coverage percentage plus a gap-analysis table naming which tickets are under-specified and who owns them.
Running it again. Re-run whenever the sprint's stories change. --mode create skips stories that already have test cases; --mode update re-drafts only those whose acceptance-criteria hash changed and flags the rest as 'may be stale — review recommended.'
Plug it into your stack. Pipe its output into the Test Scheduler — once test cases exist and are counted, the scheduler balances who tests what and by when. Wire the --mode create step into sprint-kickoff automation so drafts are waiting on day one.

Under the hood — for the curious

A slide for each moving part. Slide back and forth.

1 / 5

Queries Azure DevOps

When it runs
First — once per sprint, feature, or ID list you scope it to.
Takes in
A sprint name, a feature ID, or a list of story IDs.
Shows out
Every matching user story with description, acceptance criteria, and existing linked test cases, via the ADO REST API.
2 / 5

Reads existing coverage

When it runs
Per story, before drafting anything.
Takes in
A story ID and its TestedBy relations.
Shows out
The set of test cases already linked to that story, so drafting stays idempotent.
3 / 5

Drafts test cases via the LLM

When it runs
For every story with enough detail to test.
Takes in
The story's acceptance criteria, plus business rules and edge cases from a prior feature briefing if present.
Shows out
Concrete steps, expected results, and priority — plain and, optionally, Given/When/Then form, via Gemini Flash.
4 / 5

Flags gaps and drift

When it runs
For every child work item, and every story with previously drafted tests.
Takes in
A ticket's title/description/acceptance-criteria text, and the content hash stored on its last test cases.
Shows out
A typed list of missing elements (no design reference, no acceptance criteria) and a content-hash drift flag where the wording has moved on.
5 / 5

Emits the coverage and gap report

When it runs
Once, at end of run.
Takes in
All processed stories, their linked tests, and the detected gaps.
Shows out
Markdown, JSON, and Excel reports with a coverage percentage and prioritized action items, each assigned to the owner of the fix.
