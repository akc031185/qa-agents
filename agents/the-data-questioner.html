The Data Questioner

Converts a plain-English question into a correct, read-only SQL query against the app's schema — tables, joins, and date logic already resolved.

Source file: db-query-agent.ts

Ask in natural language — 'how many people used the learning feature yesterday?' — and get back a ready-to-run SELECT. The agent parses the app's schema.sql into a table/column/foreign-key map, hands that map to the LLM as context, and constrains generation to the real schema so the query actually compiles against it. No live database connection required.

Why this exists

The chore it removes

Pulling a number from the database normally means finding someone who knows both the SQL dialect and which of hundreds of tables and columns holds the answer and how they join. They hand-write the query, fix the joins, guess the right date column, and test it. Non-technical requesters can't do any of it, so every ad-hoc question queues behind a specialist.

→
What you get instead

Type the question; get back a correct SELECT with the right tables, joins, and date logic already worked out — plus an optional plain-language explanation of what it does. One LLM round-trip, no queue.

When anyone can pull a trustworthy answer in seconds, decisions stop blocking on a short list of busy SQL specialists.

What this step does

See it in action

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • The app's schema.sql DDL export on disk in the toolkit's knowledge folder — no live database connection is needed to generate a query.
  • An ANTHROPIC_API_KEY — the agent calls Claude to generate the SQL from your natural-language question.
  • (Optional) a few trusted reference queries dropped alongside the schema so the model can match the team's house style.

Step by step

  1. Install Node.js — the runtime the agent runs on.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is a TypeScript program; Node executes it. Install once per machine.
    First run Only needed on a fresh machine.
  2. Clone the agent code and install its dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the agent's dependencies — the Claude client and the schema-file reader — into node_modules.
    First run Downloads everything (a minute or two).
    Re-run No-op once installed, unless the dependency list changed.
  3. Set the one required environment variable.
    export ANTHROPIC_API_KEY=your-claude-key
    Why The agent never touches the database — it reads schema.sql on disk, then calls the LLM to generate SQL. The API key is the only hard requirement.
  4. Run your question.
    npm run db:query -- --question "How many people used the Learning feature yesterday?" --explain --save
    Why --question is the natural-language ask. --explain appends a plain-language description of the query. --save persists it instead of only printing to the terminal.
    First run Parses the full schema fresh and issues one LLM request.
    Re-run Identical every time — no cache. A different --question just asks something new.
  5. Open the generated query.
    open ./outputs/reports/db-queries/DbQuery_<timestamp>.sql
# and the full record:
open ./outputs/reports/db-queries/DbQuery_<timestamp>.json
    Why The .sql is the ready-to-paste query. The .json is the same query plus its explanation and the tables-used list, for the record.

What you give it

--question <text>
Your natural-language question about the app's records.
--dialect
Target SQL dialect: the default, or an alternate.
--explain, --save, --list-tables, --schema
Append an explanation, persist to disk, list every table instead of querying, or filter that listing to one schema.
environment variable
The ANTHROPIC_API_KEY used to generate the query.

What comes back

printed query (and explanation)
Printed to the terminal on every run, saved or not.
DbQuery_<timestamp>.sql
The runnable query alone, ready to paste into a DB client (written only with --save).
DbQuery_<timestamp>.json
The query plus its explanation and the tables it used (written only with --save).
Running it again. Every run is a fresh LLM request — no fingerprinting or caching like some of the other agents use. Unsure of a table or column name? Run --list-tables first to see the real map before asking.
Plug it into your stack. Wire it behind a chat command or team chatbot so anyone can type a question and get back a vetted, read-only query — no queue, no waiting on the one person who knows the schema. The hard SELECT-only constraint makes it safe to expose broadly.

Parses the schema DDL

When it runs
First, on every invocation.
Takes in
The schema.sql DDL file on disk plus any trusted reference queries.
Shows out
A structured table/column/foreign-key map, extracted via pattern matching — no live database connection.
2 / 5

Builds the system prompt

When it runs
Right after the schema is parsed.
Takes in
The schema map, the reference queries, and the fixed generation rules (joins, SELECT-only, dialect).
Shows out
One system prompt carrying everything the LLM needs to emit a correct query in the target dialect (MSSQL or Postgres).
3 / 5

Calls the LLM

When it runs
Once per question.
Takes in
The question plus the system prompt, sent at temperature 0.1 to stay deterministic.
Shows out
A reply with a fenced SQL block, a declared TABLES_USED list, and an optional explanation.
4 / 5

Enforces read-only

When it runs
Built into every request — never disabled.
Takes in
The generation rules.
Shows out
A hard SELECT-only constraint — INSERT/UPDATE/DELETE/DROP/ALTER are never generated.
5 / 5

Persists the result

When it runs
Only with --save.
Takes in
The generated query, its explanation, and the tables-used list.
Shows out
A timestamped .json (full record) and .sql (runnable query) dropped into the reports folder.
