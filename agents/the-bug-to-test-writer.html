The Bug-to-Test Writer

Turns a bug ticket — text plus screenshots — into a numbered, expected-result test case via a multimodal LLM, tracker-ready.

Source file: bug-tc-generator-agent.ts

Fetches a bug from ADO, loads a local briefing on its parent story, extracts up to four screenshots, and sends all of it to Gemini 2.0 Flash multimodal to draft a structured test: title, numbered steps, per-step expected results, and a repro-quality rating. Guarantees a sign-in first step, fills gaps from the story briefing, and falls back to a rule-based skeleton if no LLM key is set.

Why this exists

The chore it removes

Every fixed bug needs a clean test so a tester can confirm it and re-run it later. But reports are messy — one-line title, no steps, an unexplained screenshot. Turning that into a numbered test with a sensible expected result per step is skilled, tedious work, repeated per bug.

→
What you get instead

A complete, ready-to-run test per bug — title, setup, numbered steps each with its own expected result, plus an honest good/partial/poor rating of the original report — serialized as Markdown, a tracker-upload Excel sheet, and optionally Word.

A written test converts a one-time fix into a permanent regression net, and the reporter-quality leaderboard quietly surfaces who writes clear reports and who needs coaching.

Run it & wire it in

This was an internal tool: the steps are real, but running it needs access to the system it targets (your tracker, the app’s API, the designs). Treat it as a faithful how-it-ran guide.

Before you start

  • Node ≥ 18 and a terminal (macOS/Linux shell or Windows PowerShell).
  • An Azure DevOps org/project and a PAT with work-item read scope.
  • One or more bug IDs — already-filed tickets with at least a title and, ideally, a description or screenshots.
  • A Google Gemini API key — bug text and screenshots are sent to the multimodal model to draft the test; without a key it drops to a rule-based skeleton.

Step by step

  1. Install Node.js — the runtime.
    # macOS (with Homebrew):
brew install node

# or download the LTS installer from nodejs.org, then check it worked:
node -v   # should print v18 or higher
    Why The agent is TypeScript on Node. One-time per machine.
    First run First time only, on a new machine.
  2. Clone and install dependencies.
    cd path/to/the-agents
npm install
    Why npm install pulls the ADO client, the Gemini client, and the xlsx/Word writers into node_modules.
    First run Full install, a minute or two.
    Re-run No-op once installed, unless the dependency list changed.
  3. Export the ADO target and the Gemini key (environment variables).
    export ADO_ORGANIZATION=my-org
export ADO_PROJECT="My Project"
export ADO_PAT=your-access-token
export GOOGLE_API_KEY=your-gemini-key
    Why Read at startup to resolve the board and the drafting model. Leave GOOGLE_API_KEY unset and it still runs on the rule-based fallback.
  4. Dry-run to fetch the bugs — no LLM call.
    npm run bug:tc -- --bug-ids "4397,4262,4488" --dry-run
    Why --dry-run fetches and reads the bugs only — no Gemini call, no files — a quick check that the IDs and access resolve.
  5. Generate the real test cases.
    npm run bug:tc -- --bug-ids "4397,4262,4488"
# skip sending screenshots to the AI:
npm run bug:tc -- --bug-ids "4397" --no-screenshots
# also produce a Word document:
npm run bug:tc:word -- --bug-ids "4397"
    Why The real run — one LLM-drafted test per bug ID, each starting with sign-in and ending with the fix confirmed.
    Re-run No caching — the same IDs re-fetch and re-draft from scratch, so an improved bug description flows through on the next run.
  6. Open the generated tests.
    open ./outputs/reports/bug-tc/BugTC_<timestamp>.md
open ./outputs/reports/bug-tc/BugTC_ADO_Upload_<timestamp>.xlsx
    Why The .md is the readable draft; the .xlsx is pre-shaped for bulk upload into the tracker as real test cases.

What you give it

--bug-ids <ids>
Comma-separated bug IDs to generate tests for (required).
--app-url <url>
Environment URL the generated test's sign-in step points at.
--no-screenshots
Skip extracting and sending screenshots — text-only draft.
--word
Also serialize a .docx.
--dry-run
Fetch bugs only — skip the LLM generation step.
environment variables
Org/project target, the PAT, and the Gemini key.

What comes back

BugTC_<timestamp>.json
Full structured test cases — title, steps, expected results, repro-quality rating per bug.
BugTC_<timestamp>.md
The same tests rendered to read and follow.
BugTC_ADO_Upload_<timestamp>.xlsx
Tracker-shaped sheet for bulk-uploading the tests as real test cases.
BugTC_<timestamp>.docx
Shareable Word version, only with --word.
Running it again. No caching — the same bug ID re-fetches the ticket and re-drafts from scratch, so an improved description or a newly-added screenshot flows through automatically on re-run.
Plug it into your stack. Trigger it the moment a bug flips to Resolved (an ADO webhook or state-change hook) with that bug's ID, then hand the .xlsx to your bulk test-case importer — 'fixed' becomes 'has a permanent regression test' with no manual writing in between.
