01
QA automation

38 single-purpose QA agents

One task each, a typed contract each — automating the repetitive parts of testing on the ADO REST API, Playwright, SQL, and an LLM where judgment is needed.

FIELD GUIDE · SOFTWARE AGENTS
02
The model

Scoped automation, not a chat assistant.

Each agent is a single-purpose CLI: typed inputs, typed outputs, one QA task. No agent framework, no chat loop — it runs, writes its artifact, and exits.

Section 01 · QA workflow stage

Finding & reporting problems

Triage and document defects: turn failed test runs into filed, linked bug tickets, re-verify fixes in a live browser before release, and generate the repro test straight from a bug report.

FIELD GUIDE · SOFTWARE AGENTS
04
Agent 01 · Finding & reporting problems

The Bug Filer

Files a typed, deduplicated ADO Bug work item per test failure — title, repro steps, severity, screenshot, parent link — in one pass.

Before

Manual triage means opening the tracker and hand-keying each failure into a new ticket: title, error, repro steps, severity, browser, screenshot, parent link. Across a dozen failures it's slow, and fatigue produces vague titles, missing screenshots, and duplicate filings.

→
After

One consistently-structured Bug work item per failure, filed the moment it lands — identical field layout every time, no duplicates, no blank fields. Severity and priority are assigned by deterministic keyword rules, so the same failure always grades the same way.

FIELD GUIDE · SOFTWARE AGENTS
05
Agent 02 · Finding & reporting problems

The Bug Analyst

Rolls every bug under a feature into a computed status report — fix rate, time-to-fix, hotspots, per-assignee load — with zero manual tallying.

Before

Briefing a lead means opening the tracker and hand-tallying: open vs fixed, severity mix, which area has the most, who's carrying the load, mean time-to-fix — then pasting it into a doc. Hours of work, stale the next day, and arithmetic errors creep in by hand.

→
After

An instant, reproducible report — totals by severity/state, fix rate, average days-to-fix, the hotspot story, per-assignee workload, plus generated insights and recommendations — as Markdown, Excel, JSON, and optionally Word. Every number is computed from live tracker data, so it's right every run.

FIELD GUIDE · SOFTWARE AGENTS
06
Agent 03 · Finding & reporting problems

The Release-Readiness Inspector

Replays every fixed bug's repro in a headless-capable Playwright browser, P1-first, and returns a pass-rate go/no-go verdict.

Before

Every release, a tester is supposed to re-open each fixed bug, read the repro, and manually click through to confirm it holds and nothing adjacent regressed. Across dozens of bugs under time pressure it gets rushed, and the urgent ones don't reliably get checked first.

→
After

An automated re-check in a real browser, priority-ordered (P1 before P2/P3/P4), with a PASS/FAIL and screenshot per bug — plus an explicit SKIP list of what a browser genuinely cannot verify and why.

Agent 04 · Finding & reporting problems

The Bug-to-Test Writer

Turns a bug ticket — text plus screenshots — into a numbered, expected-result test case via a multimodal LLM, tracker-ready.

Before

Every fixed bug needs a clean test so a tester can confirm it and re-run it later. But reports are messy — one-line title, no steps, an unexplained screenshot. Turning that into a numbered test with a sensible expected result per step is skilled, tedious work, repeated per bug.

→
After

A complete, ready-to-run test per bug — title, setup, numbered steps each with its own expected result, plus an honest good/partial/poor rating of the original report — serialized as Markdown, a tracker-upload Excel sheet, and optionally Word.

Section 02 · QA workflow stage

Deciding what to test

Turn requirements into a test plan: aggregate feature context, generate and review test cases, sharpen vague acceptance criteria against the designs, and schedule execution across the team.

FIELD GUIDE · SOFTWARE AGENTS
09
Agent 05 · Deciding what to test

The Test Scout

Collapses a feature's scattered artifacts — ADO work items, design docs, meeting transcripts — into one structured, testable briefing.

Before

A tester picks up a story with a three-line description. The real detail is spread across a Figma deck, a spec doc, an hour of recording, and child work items. Reconstructing a testable model by hand is slow and brittle — one missed decision silently changes the expected behavior.

→
After

Point it at a story ID and a document folder. It walks the ADO work-item tree, extracts text (pdf-parse for PDFs, mammoth for Word, a VTT parser for transcripts), sends transcripts to Gemini Flash for demonstrated behavior and decisions, then merges everything into a content-hashed JSON briefing: purpose, flows, business rules, edge cases, integration points, open questions, and a 0–100 confidence score. Re-runs are incremental — only changed sources are re-parsed.

FIELD GUIDE · SOFTWARE AGENTS
10
Agent 06 · Deciding what to test

The Test-Plan Author

Drafts executable test cases from ADO user stories and, for stories too thin to test, emits a gap report naming the missing fields and their owners.

Before

Hand-authoring test cases per ticket — steps, test data, expected result — is slow and repetitive. Worse, a large fraction of tickets are untestable as written: no design references, no acceptance criteria. The tester either guesses at intent or blocks to chase the developer, one ticket at a time, and the questions trickle out over days.

→
After

The agent reads each story and drafts its test cases. For stories that aren't ready, it emits a gap report keyed by story: missing/short description, no acceptance criteria, no design reference — each tagged with the assignee — so the whole batch of questions goes back to the team in one round trip instead of one at a time.

Agent 07 · Deciding what to test

The Test Scheduler

Load-balances a feature's test cases across the team by weighted priority and emits a phased schedule as Word and Excel deliverables.

Before

Before every sprint a lead builds the plan by hand: count each story's test cases, estimate capacity, assign urgent stories to the right people, sketch a timeline, enumerate risks, and format it into something management will read. It takes half a day, the weighting math is error-prone, and one tester silently ends up overloaded.

→
After

Give it the feature ID, the team roster, and the sprint dates. It reads the real test-case counts, balances load by weighted priority (P1 counts 1.5x, P4 only 0.3x), builds a phased timeline with milestones on business days, runs rule-based risk checks, and writes the Test Plan and Execution Schedule as Word and Excel — no hand-formatting.

Agent 08 · Deciding what to test

The Spec Reverse-Engineer

Reconstructs a feature's spec — description, acceptance criteria, scope — from its test cases alone, grounded only in what the tests evidence.

Before

Documenting a feature that has dozens of test cases but no spec is slow detective work: read every test, infer the behavior each one proves, group by topic, then write a description, acceptance criteria, and in/out-of-scope notes. It's manual, and two analysts produce two different write-ups.

→
After

The agent loads the test cases, buckets them by parent story, and calls the LLM to emit a description, an acceptance-criteria list, and in-scope/out-of-scope notes per group — constrained to what the tests evidence, never inventing requirements. Outputs Word, Markdown, and JSON.

Agent 09 · Deciding what to test

The Test-Case Reviewer

Splits a test-results spreadsheet into a passed-verified acceptance-criteria doc and a review sheet of everything needing a human ruling.

Before

After execution, someone sorts the results spreadsheet by hand: passes get written up as confirmed behavior; every failure or skip has to be summarized — expected, actual, tester note — and put in front of the scrum master to rule 'real bug or bad test?'. Across many tabs it's tedious and the write-ups come out inconsistent.

→
After

The agent reads the workbook and emits two documents. One is an acceptance-criteria document built only from PASS rows, in Given/When/Then form with duplicates merged. The other is a review sheet listing every non-passing test — expected result, actual result, tester comment verbatim — with tick-boxes for 'Valid Bug', 'Invalid Test', or 'Needs More Info'.

Agent 10 · Deciding what to test

The Requirements Sharpener

Rewrites a vague requirement into precise, testable Given/When/Then criteria grounded in the actual design screenshots — additively, never overwriting the original.

Before

Making a requirement like 'show an error if the input is invalid' testable means cross-referencing it against the design mockups by hand: the exact error wording, the precise button label, which states are disabled, what the empty screen reads — then rewriting each point. It's meticulous, and anything missed becomes a gap a tester hits later.

→
After

The agent pulls the requirement, the prior feature briefing, and the exported design package — including the screenshots as base64 image data — and sends them to a multimodal Gemini model that reads the pixels, not just descriptions. It returns Given/When/Then criteria that quote exact labels and messages and cite the source screen, added alongside the untouched original.

Agent 11 · Keeping the project tracker up to date

The Build Watcher

Triggers an ADO pipeline run and polls it to completion, returning a pass/fail verdict — no tab-refreshing to catch the result.

Before

Kick off a pipeline, then keep flipping to a browser tab every few minutes to check if it's done. A run can take 30 minutes. Focus drifts, failures go unnoticed for an hour, and cancelling a hung run means hunting through the ADO UI for the stop button.

→
After

The agent triggers the run, then polls getRunStatus every 30s until state === 'completed', then prints the result, elapsed time, and run URL. On request it fetches published artifacts or PATCHes a stuck run to canceling — all headless.

FIELD GUIDE · SOFTWARE AGENTS

Agent 12 · Keeping the project tracker up to date

The Test-Suite Organizer

Bulk-organizes an ADO test suite — files test cases into suites, repairs broken TestedBy links, normalizes titles to a naming convention, and reassigns testers.

Before

By hand, keeping a suite tidy is soul-crushing. Someone opens suite after suite, checks each test case's title against the convention, confirms it's linked to the right story in the right direction, and records its owner — across hundreds of items. Titles drift, links point the wrong way, and reassigning work when someone leaves means editing dozens of items one at a time.

→
After

The agent does the whole sweep in one pass. It lists suite contents, adds test cases, and — most usefully — audits every case for three defects: a missing TestedBy-Reverse link, a reversed (TestedBy-Forward) link, and a title that breaks the naming convention. It reports each, and on approval fixes them. It also reads a feature's stories to auto-assign each test case to its author, and bulk-reassigns ownership when it changes.

Agent 13 · Keeping the project tracker up to date

The Results Poster

Derives each test case's Passed/Failed outcome from the story's ADO state — QA task closure and bug links — then posts the results to a test run.

Before

A tester finishes a feature, then updates the tracker one test point at a time: open each, decide pass or fail, recall which bug maps to which test case, and click through several screens to record it. Across dozens of test cases and many features it's an afternoon of clicking — and easy to mismark or skip a few.

→
After

The agent reads each story and applies three deterministic rules. QA task Closed with no bugs → every test case Passed. Bugs linked to specific test cases → exactly those Failed, the rest Passed. QA task not Closed → skip and leave a reminder comment instead of guessing. It then posts all outcomes to a single test run.

One typed Azure DevOps client every agent shares — reads and writes work items live, or against local fixtures with zero credentials.

Before

When no PAT is present the constructor flips offline: true and routes every call through a FixtureStore over fixtures/ado/{id}.json — same methods, same return types, no network. Live and offline are chosen automatically by whether a PAT exists.

One reconciliation engine that checks a displayed value against the record behind it — seven compare modes, pure and offline, no DB required.

Before

→
After

Before

→
After
